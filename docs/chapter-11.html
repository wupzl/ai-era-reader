2026 年 11 月，凌晨 1:26。

天穹科技，人工智能架构委员会。

会议室中央悬浮着一张巨大的全息排行榜。

屏幕上排列着七种模型架构。

MODEL ARCHITECTURE EVALUATION

A. Dense Transformer
B. Mixture of Experts
C. Diffusion Language Model
D. State Space Model
E. Hybrid Architecture
F. Multimodal Model
G. World Model

林远坐在会议桌前。

他已经不是几个月前那个只会调用大模型 API 的年轻工程师了。

他亲手搭建过 RAG 系统。

开发过 Coding Agent。

研究过多 Agent 调度。

甚至参与了 Agent OS 的架构设计。

但今天，他面对的是一个更根本的问题。

如果模型架构本身都在不断变化，我们究竟应该把未来的 AI 系统建立在哪种模型之上？

首席科学家周衡走到屏幕前。

“公司计划建设下一代 AI 平台。”

“要求支持 Coding Agent、实时语音、长文档理解、机器人控制和端侧推理。”

“现在，请你们选出未来五年的核心模型架构。”

林远毫不犹豫。

“Transformer。”

会议室里安静了几秒。

周衡问：

“为什么？”

“因为目前绝大多数主流大语言模型都建立在 Transformer 或其变体之上。”

“生态成熟，训练稳定，工程支持也完善。”

周衡点头。

“那为什么还会出现 MoE、Diffusion、Mamba 和各种混合架构？”

林远停住了。

陈默坐在会议室最后一排，终于开口。

“因为 Transformer 赢得了上一场战争。”

“但它并没有消灭所有计算瓶颈。”

他站起来，在白板上写下：

模型架构的演化，本质上是对计算、记忆、并行性和表达能力之间矛盾的持续重新分配。

“今天，我们不讨论谁一定会统治未来。”

“我们要研究，为什么每一种架构都会诞生。”

第一幕：Transformer 帝国为什么能够统治世界？

meta-intelligence.tech

陈默没有直接讲 Transformer。

他先问林远：

“在 Transformer 出现之前，计算机怎样处理一句话？”

林远回答：

“早期可以使用 RNN、LSTM 这样的循环神经网络。”

“对。”

陈默写下一句话：

我昨天在图书馆借了一本关于人工智能的书。

“假设我们要理解最后的‘书’。”

“RNN 通常怎样处理？”

“从左到右，依次更新隐藏状态。”

1. RNN 的历史困境

传统 RNN 可以写成：

ht=f(ht−1,xt) h_t=f(h_{t-1},x_t)

其中：

  • xtx_t：当前 Token 的输入表示

  • ht−1h_{t-1}：之前的隐藏状态

  • hth_t：当前隐藏状态

陈默说：

“它的问题不只是长距离依赖。”

“还有时间步之间的串行依赖。”

“第 100 个 Token 的隐藏状态，依赖第 99 个。”

“这限制了训练阶段沿序列维度的并行性。”

林远说：

“LSTM 和 GRU 缓解了长期依赖问题，但没有完全消除循环计算的串行性。”

“正确。”

2. Transformer 的革命

陈默在白板上写下三个字母。

Q、K、V。

“Transformer 最重要的变化之一，是让序列中的位置通过 Attention 直接建立联系。”

经典缩放点积注意力：

Attention⁡(Q,K,V)=softmax⁡(QK⊤dk)V \operatorname{Attention}(Q,K,V) = \operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_k}} \right)V

林远看着公式。

“Query 与 Key 计算相关性，再根据权重聚合 Value。”

“对。”

“在自注意力中，Q、K、V 通常来自同一序列的不同线性投影。”

“训练时，许多 Token 的计算可以通过矩阵运算并行完成。”

3. Transformer 为什么适合 GPU？

陈默问：

“GPU 最擅长什么？”

“大规模并行矩阵运算。”

“而 Transformer 的核心操作是什么？”

“矩阵乘法。”

“这就是关键。”

Transformer 不只是理论上能够建模长距离依赖。

它还与现代加速硬件形成了非常好的配合。

陈默继续解释：

“这种配合让大规模预训练更容易扩展。”

“再加上数据规模、计算规模和模型规模的持续增长，Transformer 逐渐成为语言模型的主流基础架构。”

4. 但 Attention 有代价

林远突然问：

“如果所有 Token 都能相互关注，那序列越长，计算量不是越大吗？”

陈默点头。

对于标准全注意力，序列长度为 nn 时，注意力分数矩阵包含：

n×n=n2 n\times n=n^2

个元素。

因此，注意力相关计算通常具有关于序列长度的二次复杂度。

“不过不要把这个结论理解成整个 Transformer 在所有情况下都严格是 O(n2)O(n^2)。”

陈默提醒。

“前馈网络、投影计算、注意力优化算法和硬件实现都会影响实际开销。”

“FlashAttention 等技术可以大幅减少中间结果的显存读写，但不会凭空消除标准全注意力的全部二次计算。”

林远终于理解。

“Transformer 的成功，来自表达能力与并行计算的结合。”

“而它的局限，也来自这种全局交互的计算成本。”

第二幕：Dense Transformer——每个问题都唤醒整支军队

陈默切换到第二张图。

一个拥有数百亿参数的模型出现在屏幕中央。

“我们先讨论最常见的一类结构。”

Dense Transformer。

1. 什么叫 Dense？

林远问：

“Dense 是不是指每次推理都会用到所有参数？”

“可以这样理解其核心特点，但需要说得更准确。”

“对于一个典型的 Dense Transformer，每个 Token 在经过相应层时，通常会使用这些层的全部主要权重矩阵。”

“它不像稀疏专家模型那样，为不同 Token 动态选择不同的 FFN 专家。”

陈默画了一个比喻。

一个帝国拥有十万名士兵。

每次执行任务，都动员整支军队。

无论任务是：

翻译一句话。

写一段 Java。

解释一道数学题。

还是判断一条日志是否异常。

大部分核心网络都会参与计算。

2. Dense 的优势

陈默说：

“Dense 的优势是计算路径相对规则。”

“参数分布和执行模式更统一。”

“在许多硬件和推理框架上，容易实现稳定高效的计算。”

此外，Dense 模型没有专家路由带来的额外负载均衡和跨设备专家通信问题。

3. Dense 的代价

“但如果模型规模越来越大，每生成一个 Token 都需要访问大量权重。”

林远接上：

“这就会产生显存容量和内存带宽压力。”

“对。”

“尤其在低批量自回归解码时，权重读取可能成为重要瓶颈。”

陈默写下一个粗略关系：

Tdecode≳需要读取的权重字节数有效内存带宽 T_{\text{decode}}\gtrsim \frac{\text{需要读取的权重字节数}} {\text{有效内存带宽}}

“这是便于理解的理想化估算。”

“真实推理还受到 KV Cache、计算吞吐、通信和内核效率影响。”

林远问：

“所以 Dense 的问题是，每个 Token 都要动员太多参数？”

“这正是 MoE 试图缓解的问题之一。”

第三幕：MoE——为什么一百位专家不必同时工作？

medium.com

会议室灯光变暗。

屏幕上出现一百扇门。

每扇门后面都有一位专家。

有的擅长数学。

有的擅长代码。

有的擅长语言。

有的擅长逻辑。

林远问：

“这就是 Mixture of Experts？”

“对，但这些专家不一定能被人类明确命名为数学专家、代码专家。”

陈默说。

“在模型内部，它们通常是通过训练形成的参数子网络。”

“实际学到的分工可能非常复杂。”

1. MoE 的基本思想

假设某一层有 8 个专家网络。

每个 Token 到来时，Router 计算它应该被送往哪些专家。

例如：

Token: "HashMap"

Router Scores:
Expert 1: 0.03
Expert 2: 0.61
Expert 3: 0.04
Expert 4: 0.02
Expert 5: 0.24
Expert 6: 0.01
Expert 7: 0.03
Expert 8: 0.02

Top-2:
Expert 2
Expert 5

只有选中的专家参与这一部分的计算。

一个简化表达式：

y=∑i∈TopK⁡(g(x))wi(x)Ei(x) y=\sum_{i\in \operatorname{TopK}(g(x))} w_i(x)E_i(x)

其中：

  • g(x)g(x)：路由器

  • Ei(x)E_i(x)：第 ii 个专家

  • wi(x)w_i(x)：对应专家权重

2. MoE 为什么可能更省计算？

陈默问：

“如果一个模型总共有 100B 参数，但每个 Token 只激活其中一部分参数呢？”

林远回答：

“那它的总参数规模可以很大，但单 Token 的计算量不必与总参数规模同比增长。”

“对。”

“这就是稀疏激活的价值。”

但陈默紧接着说：

“注意，激活参数少，不代表部署时只需要存储激活的那部分参数。”

“所有可能被路由到的专家，仍然需要能够被访问。”

“所以 MoE 的总权重内存需求可能仍然很大。”

3. MoE 的新问题：专家负载不均

陈默展示了一次路由统计。

Expert 1:  5%
Expert 2: 47%
Expert 3:  3%
Expert 4:  6%
Expert 5: 25%
Expert 6:  4%
Expert 7:  5%
Expert 8:  5%

林远皱眉。

“Expert 2 太忙了。”

“对。”

“如果大量 Token 都选择同一个专家，就可能产生负载不均。”

“训练中通常需要考虑路由稳定性、负载均衡和专家容量等问题。”

4. MoE 的通信成本

如果专家分布在不同 GPU 上：

GPU 1: Expert 1, 2
GPU 2: Expert 3, 4
GPU 3: Expert 5, 6
GPU 4: Expert 7, 8

Router 可能需要把 Token 表示发送到不同设备。

专家计算完成后，再聚合结果。

“这会引入跨设备通信。”

陈默说。

“在某些部署场景中，通信可能抵消部分稀疏计算收益。”

Dense 与 MoE 的取舍

维度 Dense Transformer MoE
每 Token 计算路径 通常使用全部主要层参数 仅激活部分专家
总参数规模 与主要计算量更直接相关 可大于单 Token 激活参数量
路由机制 无专家路由 需要 Router
负载均衡 相对简单 需关注专家负载
分布式通信 常规模型并行通信 可能增加专家间通信
部署复杂度 相对直接 通常更复杂

林远点头。

“MoE 不是免费获得更大模型。”

“它是用路由和系统复杂度，换取参数规模与激活计算之间的新平衡。”

陈默笑了。

“很好。”

第四幕：Diffusion Language Model——为什么语言一定要一个字一个字生成？

computeleap.com

周衡突然提出：

“Dense 和 MoE 主要改变模型规模与计算分配。”

“但它们通常仍然使用自回归生成。”

“如果我们连生成方式都改变呢？”

林远想起第二章。

“Diffusion Language Model。”

陈默点头。

1. 自回归生成的串行性

传统自回归语言模型通常建模：

P(x1,…,xn)=∏t=1nP(xt∣x<t) P(x_1,\ldots,x_n) = \prod_{t=1}^{n} P(x_t\mid x_{<t})

这意味着生成第 tt 个 Token 时，依赖前面已经生成的 Token。

例如：

第 1 步：Java
第 2 步：Java 是
第 3 步：Java 是 一种
第 4 步：Java 是 一种 编程语言

“这个生成过程天然存在串行依赖。”

陈默说。

“即使单步计算很快，长输出仍然需要很多步。”

2. Diffusion 的另一条道路

陈默把屏幕上的句子全部遮住。

[MASK] [MASK] [MASK] [MASK] [MASK] [MASK]

然后逐步恢复：

第 1 轮：
Java [MASK] 一种 [MASK] 语言 [MASK]

第 2 轮：
Java 是 一种 [MASK] 语言 [MASK]

第 3 轮：
Java 是 一种 编程 语言 。

“这只是掩码式离散扩散模型的示意。”

陈默解释。

“不同扩散语言模型可能采用不同的噪声过程、训练目标和采样策略。”

“但核心思路是，不必严格按照从左到右的方式逐 Token 确定输出。”

3. 为什么它有吸引力？

林远回答：

“因为它有机会在一次迭代中更新多个位置。”

“对。”

“如果采样步数足够少，而且每步计算高效，就可能获得并行生成收益。”

4. 为什么没有直接取代自回归？

陈默问：

“如果扩散模型需要反复迭代 32 次呢？”

第五幕：Mamba——如果不让每个 Token 都回头看历史呢？

1. 状态空间模型

经典离散状态空间模型可以写成：

ht=Aht−1+Bxt h_t=Ah_{t-1}+Bx_t

yt=Cht+Dxt y_t=Ch_t+Dx_t

其中：

  • hth_t：隐藏状态

  • xtx_t：当前输入

  • yty_t：输出

  • A,B,C,DA,B,C,D：状态转移与输入输出映射

陈默解释：

“你可以把隐藏状态理解成对历史信息的一种压缩表示。”

“新 Token 到来时，系统更新状态。”

“无需显式保存所有历史 Token 之间的完整注意力关系。”

2. Mamba 的关键变化

“但传统状态空间模型也有局限。”

陈默继续。

“Mamba 的一个关键思想，是让部分状态空间参数依赖当前输入，从而实现选择性信息处理。”

“不同输入可以影响哪些信息被保留、更新或遗忘。”

林远问：

“这是不是有点像 LSTM 的门控机制？”

“在直觉上有相似之处。”

“但 Mamba 的具体数学结构和高效计算方式不同。”

3. 为什么 Mamba 适合长序列？

陈默说：

“某些选择性状态空间模型可以避免标准全注意力那种显式的 n×nn\times n 注意力矩阵。”

“因此，它们在长序列处理和缓存开销方面具有潜在优势。”

“同时，Mamba 通过适合硬件的扫描算法，使训练阶段能够利用并行计算。”

4. Mamba 的代价

林远问：

“那为什么不全部改成 Mamba？”

陈默回答：

“因为压缩历史状态，也意味着信息访问方式发生变化。”

“Attention 可以直接对历史 Token 表示进行内容相关的访问。”

“而有限维状态必须选择如何编码历史信息。”

“对于需要精确定位、复制或检索特定历史内容的任务，不同结构可能表现不同。”

“具体效果取决于模型设计、训练方式和任务分布。”

林远点头。

“所以 Mamba 是用状态更新机制，重新分配长序列计算与记忆成本。”

1. 从语言预测到环境预测

语言模型常见目标是：

P(xt+1∣x≤t) P(x_{t+1}\mid x_{\le t})

而动作条件世界模型可以表示为：

P(st+1∣st,at) P(s_{t+1}\mid s_t,a_t)

其中：

  • sts_t：当前环境状态

  • ata_t：执行动作

  • st+1s_{t+1}：下一时刻状态

“当然，真实世界状态通常不能被完整观测。”

陈默说。

“因此实际模型可能使用历史观测、潜在状态和动作序列。”

“但要注意，这种软件环境预测不一定是机器人领域那种专门训练的世界模型。”

2. 一个简单的 Java 路由示例

public enum TaskType {
    CLASSIFICATION,
    RAG_QA,
    CODING,
    REALTIME_AUDIO,
    ROBOTICS
}

public record ModelRequest(
    TaskType taskType,
    boolean sensitive,
    long latencyBudgetMs
) {}

public String route(ModelRequest request) {

    if (request.sensitive()) {
        return "approved-private-model";
    }

    return switch (request.taskType()) {
        case CLASSIFICATION -> "small-model";
        case RAG_QA -> "general-model";
        case CODING -> "reasoning-model";
        case REALTIME_AUDIO -> "realtime-model";
        case ROBOTICS -> "robotics-model";
    };
}

第十一章：技术归档

模型架构演化脉络

RNN / LSTM

循环状态建模，缓解部分长期依赖问题

Transformer

Attention 与高并行训练

MoE

稀疏专家计算

SSM / Mamba

状态空间建模

Diffusion LM

迭代式文本生成

Hybrid

组合不同结构

多模态、推理模型和世界模型是可与多种底层结构组合的能力或建模路线，并非简单的线性继承关系。

本章最重要的五个结论

第一：Transformer 的主流地位来自表达能力、训练并行性与硬件生态的共同作用。

第二：MoE、Mamba、Diffusion LM 解决的是不同瓶颈，不能简单用一张排行榜判断谁全面更优。

第三：多模态、Reasoning Model 和 World Model 不一定是互斥的底层架构类别。

第四：训练效率、推理效率、内存占用和模型质量必须分别评估。

第五：AI 应用平台应尽可能减少对单一模型和单一架构的依赖，通过统一接口、模型路由与评测持续演进。
