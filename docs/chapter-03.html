2026 年 7 月，凌晨 3:17。

林远被一阵手机震动惊醒。

屏幕上是一条来自 Coding Agent 的通知。

任务已完成。

已修改 17 个文件，运行 142 项测试，修复 3 个失败用例，创建 Pull Request #284。

等待代码审查。

林远愣住了。

他清楚地记得，昨晚十一点，他已经关闭了电脑。

而且，他甚至没有告诉 Agent 应该如何修复那三个失败的测试。

它居然自己完成了？

第二天，林远冲进办公室。

“陈工，我们的 Agent 已经不需要我一直盯着了！”

陈默放下咖啡。

“你觉得，这意味着什么？”

“意味着模型已经能够自主工作了。”

“不完全对。”

陈默走到白板前，写下几个字：

模型不等于 Agent。Agent 也不等于常驻 Agent。

“今天，我们要讨论的，不是怎样让模型更聪明。”

“而是怎样让一个原本只能回答问题的模型，变成能够持续执行任务的系统。”

第一幕：Chatbot 的宿命——回答完就消失

故事要从几年前说起。

那时，AI 系统的结构非常简单。

用户发送一句话：

帮我写一个 Java 线程池示例。

服务器调用大模型。

模型生成代码。

服务器返回结果。

请求结束。

整个流程可能只需要几秒钟。

用户发送请求

应用服务器

组织 Prompt、调用模型 API

LLM 推理

生成文本或代码

返回结果，请求结束

林远看了一眼。

“这不就是普通的 Spring Boot 接口调用？”

“没错。”

陈默写下一段代码。

@PostMapping("/chat")
public String chat(@RequestBody ChatRequest request) {
    return llmClient.generate(request.message());
}

“对于普通问答，这种结构完全合理。”

“但假设用户的要求变成了——”

帮我分析整个 Spring Boot 项目，找出所有潜在的并发问题，修复它们，运行测试，最后提交 Pull Request。

林远思考了一会儿。

“这就不是一次 LLM 调用能完成的了。”

“为什么？”

“因为它要读文件、分析代码、调用工具、执行测试，可能还需要反复修改。”

陈默点头。

“于是，研究人员给模型增加了工具调用能力。”

第二幕：ReAct 的诞生——模型学会使用工具

aidevstack.vercel.app

2026 年之前，Agent 技术已经经历过几轮重要演进。

其中一条具有代表性的路线，就是 ReAct。

它的核心思想并不复杂：

模型不只是输出最终答案，而是在推理与行动之间循环。

陈默写下一个例子。

用户要求：

修复项目中 Redis 缓存失效导致的数据库压力问题。

Agent 开始工作。

Thought:
我需要先定位缓存相关代码。

Action:
search_files("RedisTemplate")

Observation:
找到 CacheService.java

Thought:
需要检查缓存失效和数据库查询逻辑。

Action:
read_file("CacheService.java")

Observation:
发现缓存未命中时直接查询数据库。

林远接过话。

“然后模型继续思考，决定下一步调用什么工具。”

“对。”

陈默画出一个循环。

LLM 决策下一步操作

调用工具

读取文件、搜索代码、执行命令

观察工具结果

继续决策，直到完成或停止

“现在 Agent 能完成多步骤任务了。”

林远说。

“但还存在一个问题。”

“什么问题？”

“假设它已经运行了二十分钟，正在执行第六十次工具调用。”

“这时候，用户关闭浏览器。”

“会发生什么？”

林远犹豫了。

“如果 Agent 的执行生命周期和 HTTP 请求绑定，那可能会被取消。”

“没错。”

“再假设服务器重启呢？”

“内存里的执行状态可能全部丢失。”

陈默点头。

“这就是下一场革命的起点。”

第三幕：HTTP 请求不应该决定 Agent 的寿命

凌晨两点，林远在白板前重新设计系统。

原来的架构是：

HTTP Request
    |
    v
Agent Loop
    |
    v
HTTP Response

“这有什么问题？”陈默问。

林远回答：

“Agent 的生命周期被绑定在 HTTP 请求上。”

“假设用户需要 Agent 执行一个四小时的任务，那么 HTTP 请求就得维持四小时。”

“但连接可能断开，网关可能超时，服务可能重启。”

“所以呢？”

林远写下新的设计。

把任务提交与任务执行分离。

用户提交任务

POST /agent/tasks

创建任务记录

数据库持久化 + 返回 taskId

任务调度器

分配 Worker、控制并发

Agent Worker

循环推理、执行工具、保存状态

持久化结果 + 通知用户

陈默问：

“现在用户关闭浏览器会怎么样？”

“任务继续执行。”

“为什么？”

“因为任务已经不依赖用户的 HTTP 连接，而是由后台 Worker 负责。”

“很好。”

1. 异步任务 API

林远设计了一个接口：

POST /api/agent/tasks

请求：

{
  "repository": "payment-service",
  "instruction": "修复支付回调幂等性问题"
}

服务器立即返回：

{
  "taskId": "task_1024",
  "status": "QUEUED"
}

之后，用户可以查询：

GET /api/agent/tasks/task_1024

返回：

{
  "taskId": "task_1024",
  "status": "RUNNING",
  "currentStep": "RUNNING_TESTS"
}

林远很满意。

“这样就能支持长任务了。”

陈默却摇头。

“你只是解决了连接生命周期的问题。”

“还有什么？”

“如果执行任务的 Worker 崩溃了呢？”

林远沉默了。

第四幕：Agent Runtime——数字员工的操作系统

skywork.ai

“你现在需要的，不再是一个简单的 while 循环。”

陈默说。

“而是一个真正的 Agent Runtime。”

林远问：

“Agent Runtime 和 LLM SDK 有什么区别？”

“LLM SDK 负责和模型通信。”

“Agent Runtime 则负责整个任务的执行生命周期。”

它需要回答一系列问题：

  • 当前任务执行到了哪里？

  • 下一步应该调用什么工具？

  • 工具调用是否成功？

  • 是否需要用户确认？

  • 失败后能否重试？

  • 服务器重启后能否恢复？

  • 任务是否超时？

  • 如何防止 Agent 无限循环？

陈默写下一段伪代码：

while (!task.isTerminal()) {

    AgentState state = stateStore.load(task.id());

    ModelDecision decision = model.decide(state);

    ToolResult result = toolExecutor.execute(decision);

    stateStore.save(
        state.apply(decision, result)
    );
}

“这就是一个极度简化的 Agent Runtime。”

林远看了一眼。

“核心还是 ReAct 循环，只不过每次执行都需要管理状态。”

“对，但生产系统还需要更多东西。”

陈默将 Runtime 拆成几个模块。

模块 职责
Agent Loop 驱动模型决策与工具执行
State Store 保存任务、步骤和执行状态
Scheduler 调度任务与分配 Worker
Tool Executor 调用工具并处理结果
Sandbox Manager 管理隔离执行环境
Checkpoint Manager 保存可恢复的执行进度
Permission Manager 控制高风险操作
Observability 记录日志、指标与执行轨迹

“你可以把它理解成一个微型操作系统。”

“模型像 CPU 吗？”林远问。

“这个比喻不太准确。”

陈默解释：

“模型更像决策引擎，而 Runtime 是负责调度、状态、资源、权限和执行控制的系统。”

“模型决定想做什么。”

“Runtime 决定能不能做、如何做、何时做，以及失败之后怎么办。”

第五幕：一场服务器重启引发的灾难

下午四点。

林远的 Agent 正在执行一个大型 Java 项目重构任务。

任务已经运行了 47 分钟。

它完成了：

✓ 分析项目结构
✓ 定位目标模块
✓ 修改 12 个文件
✓ 运行单元测试
→ 正在修复测试失败

突然，服务器发生故障。

Worker 进程被终止。

一分钟后，服务重新启动。

林远打开任务页面。

Task: task_1024
Status: UNKNOWN

“完了。”

他捂住额头。

“之前四十多分钟的工作是不是白做了？”

陈默走过来。

“这取决于你有没有保存状态。”

“我保存了聊天历史。”

“只有聊天历史？”

“对。”

“那还不够。”

1. 聊天历史不等于执行状态

陈默在白板上写下：

Conversation History ≠ Execution State

“假设 Agent 最后一条消息是：”

我准备修改 PaymentService.java。

“然后服务器崩溃。”

“恢复时，你怎么知道文件是否已经修改？”

林远回答：

“读取文件看看？”

“可以，但如果是外部操作呢？”

“比如 Agent 已经发送了一封邮件、创建了一张工单、触发了一笔测试支付。”

“这些操作可能已经成功，只是结果还没来得及写入数据库。”

林远立刻意识到问题。

“如果恢复后重新执行，就可能重复操作。”

“对。”

这就是分布式系统中的经典难题：

执行成功，但确认结果丢失。

2. Checkpoint 机制

陈默提出新的方案。

每执行完一个关键步骤，都保存 Checkpoint。

例如：

{
  "taskId": "task_1024",
  "step": 42,
  "status": "RUNNING",
  "workspace": "ws_1024",
  "lastCompletedAction": "read_file",
  "pendingAction": "run_tests"
}

同时保存：

  • 当前任务目标与约束

  • 模型上下文引用

  • 工具调用记录

  • 已完成步骤

  • 待执行动作

  • 工作区快照或引用

  • 权限确认状态

林远问：

“是不是只要有 Checkpoint，就能做到精确恢复？”

陈默摇头。

“不能这么简单。”

“Checkpoint 只能告诉你系统记录了什么，不能保证外部世界和记录完全一致。”

“如果工具执行成功，但状态尚未提交，仍然存在不确定性。”

“所以需要幂等设计、操作 ID、外部状态查询、必要时的补偿机制。”

第六幕：状态机——让 Agent 不再失控

林远决定重新设计任务状态。

以前，他只使用三个状态：

PENDING
RUNNING
COMPLETED

陈默看完后问：

“等待人工确认属于什么状态？”

“RUNNING？”

“那任务被暂停呢？”

“还是 RUNNING？”

“Worker 崩溃等待恢复呢？”

林远发现，三个状态根本无法表达真实情况。

于是，他们设计了一套更完整的状态机。

Agent 任务状态机

QUEUED

RUNNING

WAITING_APPROVAL

等待用户确认

RETRY_PENDING

等待重试

PAUSED

主动暂停

COMPLETED

FAILED

CANCELLED

简化示意：RUNNING 可进入等待、重试、暂停或终态；非终态可按规则恢复。实际系统应明确每条合法状态转移。

林远说：

“这和订单状态机很像。”

“没错。”

陈默回答：

“一个长任务 Agent，本质上也需要严肃的业务状态管理。”

“你以前在高并发权益发放系统里处理过状态机、幂等和重试，这些经验可以直接迁移过来。”

“区别在于，Agent 的每一步可能由模型动态决定，任务路径不是预先固定的。”

林远点头。

“也就是说，传统工作流的流程图通常比较明确，而 Agent 的行动序列具有动态性。”

“对，但动态性不意味着可以不受约束。”

第七幕：消息队列——Agent 的任务调度中心

夜晚，实验室接到了一批新任务。

一千名用户同时提交 Coding Agent 请求。

每个任务预计需要二十分钟。

林远的第一反应是：

“加服务器？”

陈默问：

“如果当前只有 50 个可用执行环境呢？”

“那就只能同时运行 50 个任务。”

“剩下的 950 个怎么办？”

“排队。”

陈默点头。

“这就是消息队列可以发挥作用的地方。”

1. 为什么长任务 Agent 需要队列？

传统 Web 接口通常追求短时间完成请求。

而 Agent 任务可能持续数分钟甚至数小时。

如果每个 HTTP 请求直接启动一个 Agent，系统很容易出现：

  • Worker 资源耗尽

  • 沙箱数量超过限制

  • 模型 API 并发过高

  • 任务无法统一调度

  • 服务重启导致执行中断

因此，可以使用队列解耦任务提交与执行。

用户提交 1,000 个任务

任务数据库 + 消息队列

任务持久化、等待调度

Worker A

Agent Runtime

Worker B

Agent Runtime

Worker C

Agent Runtime

沙箱池 / 模型服务 / 工具服务

林远说：

“这和秒杀系统的削峰填谷很像。”

“有相似之处，但这里的主要矛盾不一定是瞬时 QPS。”

陈默解释：

“即使每秒只有几个新任务，只要每个任务执行时间足够长，也可能积累大量并发任务。”

他写下一条公式：

L=λW L=\lambda W

“这是 Little 定律。”

“假设平均每秒有 2 个新任务进入系统，每个任务平均停留 600 秒。”

“那么稳定状态下，系统平均有多少任务？”

林远心算了一下。

“1,200 个。”

“对。”

“所以 Agent 系统的压力，不仅取决于请求到达速度，还取决于任务持续时间。”

2. RabbitMQ、Kafka 还是 Redis？

林远问：

“那我们是不是必须上 Kafka？”

“当然不是。”

陈默回答：

“选择中间件要看语义和规模。”

方案 更适合的场景
数据库任务表 小规模、低并发、实现简单
Redis Streams 轻量任务队列、消费者组
RabbitMQ 工作队列、确认、重试与路由
Kafka 大规模事件流、日志与事件回放
专用工作流引擎 长任务恢复、状态管理、定时与重试

“如果只是几十个任务，数据库任务表加 Worker 轮询可能已经足够。”

“消息队列不是为了显得架构高级。”

“而是为了解决真实的解耦、缓冲、可靠投递和调度问题。”

第八幕：云端沙箱——给 Agent 一台真正的电脑

hackyjs.com

凌晨一点。

Agent 正在修复一个 Java 项目。

它需要执行：

mvn test

随后，它还要运行：

git diff

以及：

npm install

林远突然想到：

“这些命令到底在哪里执行？”

陈默回答：

“如果直接在 Agent 服务所在的主机执行，那就非常危险。”

“为什么？”

“因为模型生成的命令不一定可靠。”

“它可能误删文件，安装恶意依赖，访问不该访问的目录，甚至试图读取环境变量中的密钥。”

林远点头。

“所以需要沙箱。”

1. Sandbox 的本质

沙箱的目标是：

允许 Agent 执行必要操作，同时限制它对宿主系统和其他任务的影响。

常见实现包括容器、虚拟机和微虚拟机。

陈默列出几种方案。

隔离方式 特点
进程隔离 成本低，但边界较弱
Docker / OCI 容器 启动快，生态成熟，共享宿主内核
gVisor 等用户态内核方案 加强系统调用隔离
Firecracker 微虚拟机 更强的虚拟化隔离，适合多租户
完整虚拟机 隔离边界较强，但资源成本通常更高

“注意，容器并不是绝对安全边界。”

陈默强调。

“尤其在执行不可信代码时，需要考虑内核漏洞、网络权限、挂载目录、凭证暴露等问题。”

2. 每个 Agent 拥有独立工作区

林远设计了一个新的运行方式。

task_1024
 ├── workspace/
 │    ├── src/
 │    ├── pom.xml
 │    └── README.md
 ├── logs/
 ├── artifacts/
 └── checkpoint/

“每个任务都有自己的工作区。”

“不错。”

“但是，如果两个 Agent 同时修改同一个 Git 仓库呢？”

林远回答：

“可以使用独立 Git worktree 或独立仓库副本。”

“对。”

“这样可以减少文件冲突，并支持并行执行。”

“不过最终合并代码时，仍然需要处理版本冲突。”

第九幕：Agent 的死亡与复活

这是整个项目最困难的一天。

林远故意终止了一个正在执行的 Agent Worker。

屏幕上显示：

Worker terminated unexpectedly.

他重新启动 Worker。

任务却没有继续。

陈默问：

“你保存了 Checkpoint，为什么还是无法恢复？”

林远回答：

“因为沙箱也被销毁了。”

“没错。”

“所以 Agent 的状态并不只存在数据库里。”

陈默写下：

Agent State = 逻辑状态 + 外部执行状态

逻辑状态包括：

  • 当前目标

  • 已完成步骤

  • 模型上下文

  • 工具调用记录

外部执行状态包括：

  • 文件系统修改

  • Git 工作区

  • 运行中的进程

  • 外部 API 操作

  • 沙箱环境

“恢复 Agent，不等于重新加载一段聊天记录。”

“而是恢复一个分布式执行过程。”

1. Lease 与心跳

为了避免多个 Worker 同时执行同一个任务，林远引入了 Lease。

每个 Worker 领取任务时，获得一个有有效期的执行租约。

运行过程中定期续租。

如果 Worker 崩溃，租约到期，其他 Worker 才能接管。

Task: task_1024

Owner: worker_07
Lease: 30 seconds
Heartbeat: every 10 seconds

陈默补充：

“租约过期不代表旧 Worker 一定已经停止。”

“所以最好还要使用 fencing token 等机制，防止旧 Worker 恢复后继续写入。”

“这在分布式任务执行中非常重要。”

2. 任务恢复流程

检测 Worker 心跳超时

确认租约失效并安全接管

加载 Checkpoint 与执行日志

恢复工作区或重新构建沙箱

核对未确认的外部操作

从安全的执行边界继续任务

林远说：

“这是不是意味着我们可以实现 exactly-once？”

陈默摇头。

“不能直接这么说。”

“在存在外部副作用的情况下，端到端严格 exactly-once 很难保证。”

“工程上更常见的是至少一次执行配合幂等处理，或者使用事务、操作去重、补偿等手段达到业务层面的正确性。”

第十幕：真正的长期自主执行

aistrategicinsight.com

三个月后。

林远的 Agent 已经可以稳定执行长任务。

它能够：

  • 在后台持续运行

  • 处理工具调用失败

  • 保存并恢复任务状态

  • 在沙箱中执行代码

  • 等待用户审批

  • 完成任务后发送通知

林远兴奋地说：

“现在它已经是一个真正的数字员工了！”

陈默却提出最后一个问题。

“假设用户告诉它：”

接下来一个月，持续优化这个项目的测试覆盖率。

“它能做到吗？”

林远想了想。

“目前还不行。”

“为什么？”

“因为它只能执行一个明确的任务，还不能很好地管理长期目标。”

陈默点头。

“这就是长期自主 Agent 和普通异步 Agent 的区别。”

1. 长期目标不是一个无限循环

一个真正的长期任务系统，还需要：

目标分解

把“提高测试覆盖率”拆成可以验证的子任务。

进度评估

定期判断是否取得了实际进展，而不是无限调用工具。

预算控制

限制模型调用次数、执行时间、Token 消耗和沙箱资源。

记忆管理

保存已经尝试过的方法、失败原因和项目知识。

任务重规划

当环境变化或目标无法完成时，调整后续行动。

人类监督

涉及高风险操作时暂停，等待授权。

陈默说：

“长期自主，不是让 Agent 永远运行。”

“而是让它能够在有限资源和明确约束下，持续推进一个目标。”

Agent 的智能来自模型，但 Agent 的可靠性来自系统工程。

第三章：技术归档

技术 解决的问题 与传统后端的联系
Agent Runtime 多步骤执行与生命周期管理 工作流引擎
异步任务 长任务脱离 HTTP 请求 异步任务处理
State Store 状态持久化 数据库、Redis
Checkpoint 崩溃后恢复 快照、日志恢复
Message Queue 解耦与任务缓冲 RabbitMQ、Kafka
Lease / Heartbeat Worker 故障检测与接管 分布式锁、租约
Sandbox 隔离不可信执行 容器、虚拟化
Idempotency 防止重复副作用 唯一约束、幂等键
Human-in-the-loop 高风险操作审批 审批流、权限系统
Observability 追踪 Agent 行为 日志、指标、Tracing

本章最重要的三个结论

第一，常驻 Agent 并不意味着模型一直在推理。

模型可以按需被调用。任务等待、定时唤醒、工具执行和状态保存，都由 Runtime 负责。

第二，Agent Runtime 本质上是一个面向不确定性任务的执行系统。

它既需要传统后端的状态机、调度、幂等、消息队列，也需要模型推理、工具调用和上下文管理。

第三，长期自主能力不等于无限制自动化。

真正可用的 Agent 必须有明确的目标、权限边界、预算、恢复机制和人工接管能力。
