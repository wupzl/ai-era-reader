一个价值千万的布尔值

决策模型、推理成本与 Agent 安全

2026 年 4 月。

人类已经习惯了大语言模型。

它们能写代码、回答问题、阅读文档、分析数据，甚至能够操作电脑。

然而，一场新的技术革命正在悄悄发生。

这一次，研究者们不再满足于让 AI 变得更聪明。

他们开始追问一个更根本的问题：

为什么所有任务，都必须交给一个不断生成文字的大模型？

于是，AI 世界逐渐分裂出了不同的技术路线。

语言模型派

“给我问题，我通过生成 Token 来回答。”

决策模型派

“如果只需要判断，就没必要生成一大段文字。”

Agent 派

“回答问题只是开始，我要真正完成任务。”

世界模型派

“文字无法描述整个世界，我要理解空间、运动与物理规律。”

而在这些派系之外，还有扩散语言模型、实时多模态、端侧小模型、Agent 记忆、运行时沙箱等技术路线。

它们并非互相取代，而是在解决不同的问题。

我们的故事，就从一个看似微不足道的判断任务开始。

故事开始

1. 昂贵的判断

2026 年，某大型互联网公司。

凌晨两点，AI 基础设施部门依然灯火通明。

工程师林远盯着屏幕。

屏幕上是一套刚刚投入生产的 Coding Agent 系统。

这套系统已经能够自动阅读代码、修改文件、运行测试，甚至提交 Pull Request。

但它有一个严重的问题。

太贵了。

每天数百万次模型调用，让推理成本不断上涨。

林远决定调查。

他打开了调用日志。

请求：是否允许 Agent 执行 rm -rf /tmp/build？

模型输出：
经过分析，该命令主要用于清理临时
构建文件，目标路径位于 /tmp/build，
通常不会影响其他业务数据。

因此，我认为可以允许执行。

最终判断：允许

林远皱起眉头。

“我只是想知道能不能执行，为什么要给我生成这么多文字？”

坐在旁边的架构师陈默回答：

“因为我们用的是语言模型。”

“语言模型有什么问题？”

“不是说语言模型不好，而是我们把所有问题都当成了语言生成问题。”

陈默走到白板前，写下：

P(xt+1∣x1,…,xt) P(x_{t+1}\mid x_1,\ldots,x_t)

“传统自回归语言模型的核心工作，是根据已有上下文预测下一个 Token。”

“哪怕你只需要一个布尔值，它通常也需要通过生成 Token 的方式表达结果。”

林远想了想。

“那我直接要求它只输出 true 或 false，不就行了？”

陈默点头。

“当然可以。约束输出、分类头、小模型分类器，早就能解决这类问题。”

“所以真正值得研究的不是能否输出布尔值，而是：能否以更合适的模型结构、更低的延迟和成本，完成高可靠性的决策？”

2. 决策模型的登场

venturebeat.com

陈默继续写下一个例子。

假设 Coding Agent 准备执行以下操作：

git push --force origin main

传统做法是把命令交给 LLM，让它分析风险。

但另一种思路是让专门的决策模型接收结构化输入：

{
  "command": "git push --force origin main",
  "branch": "main",
  "protected": true,
  "environment": "production"
}

输出：

{
  "decision": "deny",
  "confidence": 0.98
}

“看见了吗？”

“它不需要生成长篇解释，而是直接完成分类或评分。”

林远眼睛一亮。

“这不就是 Jev 这类技术路线想解决的问题？”

“可以这样理解。但要注意，输出置信度不代表模型天然经过概率校准，更不能保证 0.98 就意味着 98% 的实际正确率。”

陈默在白板上画出了两个流程。

路线 A：语言模型决策

用户请求 → LLM 推理 → 生成文本 → 解析结果

路线 B：专用决策模型

用户请求 → 决策模型 → 标签 / 分数

两条路线都可以完成分类；实际性能取决于模型、部署方式和任务。

“那么，决策模型会取代 LLM 吗？”

“不会。”

陈默摇头。

“如果你需要它解释一段复杂代码、生成架构设计，甚至自主修复 Bug，语言生成依然非常重要。”

“但是，如果任务只是路由、风险评分、二分类、执行门控，专用模型可能更合适。”

林远突然想到一个问题。

“那我们之前使用的 Redis Lua、规则引擎，是不是也能完成这些判断？”

“没错，而且对于确定性安全规则，它们通常更可靠。”

陈默补充：

“例如生产分支禁止强推，就应该由权限系统和分支保护强制执行，而不是相信一个概率模型。”

“决策模型更适合处理规则难以完整表达的语义判断，但不能替代硬性安全边界。”

3. 从 Jev 到 Agent 安全体系

第二天，团队召开了架构评审会。

林远提出一个新方案。

“我们现在的 Coding Agent 有五层权限确认机制。可以把模型判断作为其中一层，但最终执行仍由确定性策略控制。”

他在屏幕上展示架构：

Coding Agent 发起工具调用

规则引擎：确定性安全检查

命令黑名单、路径权限、环境隔离

语义决策模型

风险分类、意图识别、置信度评估

低风险

允许执行

不确定

人工确认

高风险

拒绝执行

“这样既保留了模型的语义理解能力，也避免让模型成为唯一的安全防线。”

陈默点了点头。

“这才是工程化。”

“AI 时代最危险的误区之一，就是把模型的判断当成系统的保证。”

4. 第一章结束：技术知识归档

故事讲完，林远在自己的技术笔记中写下：

技术概念 本质 典型用途
LLM 语言建模与生成 编程、问答、推理
Jev 类决策路线 结构化判断与评分 路由、分类、门控
Span-01 类轨迹分类器 Agent 行为分析 轨迹评测、风险检测
AnyJev / LLM2Jev 类工具 模型能力转换或适配 决策服务部署
Agent 安全沙箱 执行环境隔离 限制工具访问与破坏范围

本章真正要记住的：

并不是所有 AI 任务都需要生成语言。一个成熟的 AI 系统，应当根据任务特点，选择规则、分类器、专用模型或通用 LLM，而不是把所有工作都交给最强的大模型。
