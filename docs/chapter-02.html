2026 年，AI 世界发生了一件奇怪的事。

过去几年，人们一直在努力让大语言模型变得更聪明。

从 GPT 到 Claude，从 DeepSeek 到 Qwen，模型的参数规模越来越大，推理能力越来越强，能够解决的问题也越来越复杂。

然而，一个看似简单的问题，却始终困扰着研究人员。

为什么一个能够在几秒钟内理解数万字文档的模型，输出答案时，却还要一个 Token、一个 Token 地往外吐？

有人开始怀疑：

也许，问题不在于模型不够聪明。

而在于它们生成语言的方式，从一开始就受到了某种限制。

于是，一条曾经主要活跃于图像生成领域的技术路线，开始向语言模型发起挑战。

它的名字叫——

扩散语言模型（Diffusion Language Model，DLM）。

林远不服气。

“如果选择了‘贷款’，后面的内容可能完全不同。”

“你还没有确定前面的内容，就同时生成后面的一百个词，可能产生大量不一致。”

这就是自回归模型采用顺序生成的一个重要原因。

后面的语言，依赖前面已经确定的语言。

当然，这并不意味着并行生成完全不可能。

推测解码、多 Token 预测、块级生成等技术，都在尝试减少顺序执行的开销。

但研究人员开始思考一个更加激进的方案。

既然逐 Token 生成存在顺序瓶颈……

为什么一定要从左到右生成？

2. 扩散语言模型的数学直觉

对于一种简化的掩码扩散过程，可以把训练分成三步：

  1. 从训练文本中抽取完整序列。

  2. 随机选择噪声水平，遮盖一定比例的 Token。

  3. 训练模型根据未遮盖的上下文，预测被遮盖的内容。

模型学习的是类似下面的条件分布：

[ p_\theta(x_{\text{masked}}\mid x_{\text{visible}},t) ]

这里的 (t) 表示噪声水平或扩散阶段。

与标准自回归模型不同，掩码位置的预测可以利用左右两侧已经可见的上下文。

不过，在生成阶段，如果多个位置同时预测，仍可能出现相互矛盾的问题。

因此，模型通常需要多轮修正、重新掩码或者逐步确定部分 Token。

扩散语言模型不是没有顺序计算，而是把逐 Token 的顺序依赖，改造成多轮文本精炼。

第四幕：Mercury 的挑战

techinvestments.io

2026 年，实验室里出现了一份关于 Mercury 系列扩散语言模型的研究资料。

陈默把它放在林远面前。

“这就是我们要研究的另一条路线。”

“它和 GPT、Claude 最大的区别是什么？”

“首先，不是名字，不是参数量，也不是排行榜成绩。”

“而是生成机制。”

Mercury 所代表的扩散语言模型路线，尝试利用并行的 Token 预测和迭代精炼，减少对严格逐 Token 解码的依赖。

林远立即想到一个问题：

“如果一次可以预测多个 Token，是不是一定比自回归模型快？”

“未必。”

1. 为什么扩散模型可能更快？

陈默写下一个简化的例子。

假设要生成 1,000 个 Token。

传统自回归模型需要约 1,000 次顺序解码步骤（不考虑特殊的并行解码优化）。

而某个假想的扩散模型，可以一次处理一个 1,000 Token 的候选块，并进行 20 轮精炼。

这是教学假设，不是 Mercury 的实测性能。每一步的计算量不同，不能由步骤数直接推导出加速倍数。

林远兴奋地说：

“那岂不是快了 50 倍？”

陈默摇头。

“你忽略了每轮计算的成本。”

“自回归模型可以利用 KV Cache，避免每次重新计算全部历史上下文。”

“而某些扩散方案需要反复处理一个较大的 Token 块。”

“所以虽然顺序轮次更少，但单轮计算可能更重。”

2. 真正的性能取决于什么？

陈默列出了四个关键因素：

  • 精炼轮数： 需要多少轮才能生成高质量结果？

  • 并行效率： GPU 能否高效地同时处理多个位置？

  • 缓存与计算复用： 能否避免每轮重复计算大量内容？

  • 质量要求： 减少精炼轮次后，准确性会下降多少？

“所以 Mercury 类模型真正需要证明的，不只是并行生成可行。”

“还要证明它在实际硬件、真实任务、相同质量要求下，具有足够好的延迟和吞吐表现。”

林远点了点头。

“也就是说，不能只看每秒输出多少 Token。”

“没错。还应该看端到端延迟、首个可用结果的时间、正确率、吞吐、GPU 成本。”

第五幕：一个致命的反击——KV Cache

当天晚上，团队召开技术讨论会。

负责传统大模型推理的工程师周航提出了反对意见。

“你们把自回归模型想得太落后了。”

“现在有 FlashAttention、PagedAttention、连续批处理、推测解码，还有越来越成熟的 KV Cache 管理。”

“凭什么认为扩散模型一定更好？”

林远一时语塞。

陈默却笑了。

“你说得对。”

他在白板上写下：

KV Cache。

1. 自回归模型为什么需要缓存？

假设模型已经生成：

Java 中的 HashMap 底层使用……

现在它准备生成下一个 Token。

如果每次都重新计算之前所有 Token 的注意力相关投影，开销会很大。

因此，Transformer 解码器可以缓存之前 Token 的 Key 和 Value。

下一步生成时，只需要计算新 Token 对应的内容，并使用已有缓存参与注意力计算。

KV Cache 的基本工作方式

历史 Token

缓存 K、V

新 Token

计算新 K、V

利用历史缓存完成当前注意力计算

周航继续说：

“你们的扩散模型如果每一轮都重新处理整个生成块，未必比我的增量解码便宜。”

陈默回答：

“所以扩散语言模型仍然面临计算复用、缓存设计和精炼调度等工程挑战。”

“但反过来，自回归模型也没有消除逐 Token 的串行依赖。”

两人对视一眼。

他们终于意识到：

这不是一种技术彻底淘汰另一种技术的战争，而是两套不同计算结构之间的竞争。

林远沉思片刻。

“所以应该做 A/B 测试。”

“对。”

“相同的 SWE-bench 任务，相同的工具权限、相同的时间预算，比较成功率、Token 成本、GPU 消耗和总执行时间。”

“这才是工程师该做的事情。”

第七幕：扩散模型真的能随意修改中间内容吗？

林远突然提出一个问题。

“既然扩散语言模型可以同时修改多个位置，那是不是意味着它特别适合代码重构？”

陈默没有直接回答。

他打开一段代码：

public int calculate(int a, int b) {
    return a + b;
}

“假设我们想把 calculate 改成 sum。”

“除了函数定义，还要修改所有调用位置。”

“扩散模型能够联合预测多个位置，这是潜在优势。”

“但它能否保证所有调用点一致？”

林远摇头。

“不能保证。”

“没错。”

“多位置联合预测并不等于拥有全局一致性保证。”

“代码重构还需要符号解析、AST、类型检查、编译器以及测试系统。”

陈默继续说：

“更重要的是，模型是否支持对已有代码进行编辑，还取决于训练目标、上下文组织和推理接口。”

“不能因为一个模型使用扩散生成，就认为它天然具有可靠的任意位置编辑能力。”

林远终于明白了。

模型的生成机制提供能力上的可能性，但工程系统决定这些能力能否可靠落地。

第八幕：两条路线的最终对决

几周后，林远整理出一份技术对比报告。

比较维度 自回归语言模型 掩码扩散语言模型
生成方式 按顺序逐 Token 生成 多轮恢复或精炼 Token
顺序依赖 输出存在严格的前缀依赖 通常按精炼轮次推进
并行生成 受顺序解码限制 可同时预测多个位置
上下文使用 因果注意力为主 可利用已知位置的双向上下文
KV Cache 增量解码生态成熟 缓存复用方式依架构而异
推理延迟 受 Token 数和解码速度影响 受轮次、块大小及单轮成本影响
代码编辑 已有成熟工程生态 具有潜力，但需任务验证
长文本生成 生态成熟，支持流式输出 长度扩展、分块与质量控制仍是挑战
典型代表 GPT、Claude 等 Mercury、LLaDA 等扩散路线

陈默看完报告，问了最后一个问题。

“所以，扩散语言模型会取代 GPT 吗？”

林远想了很久。

然后回答：

“现在不能这么说。”

“自回归模型的优势不只是生成质量，还有成熟的推理基础设施、工具调用能力和工程生态。”

“扩散模型则尝试用不同的计算结构，改善某些场景下的生成效率。”

“未来可能是两条路线竞争，也可能是混合架构。”

陈默笑了。

第二章·技术总结

第一：自回归模型的瓶颈不是不能并行计算。

而是标准生成过程需要依赖此前已经确定的 Token。

第二：扩散语言模型不是一次性完成所有生成。

它通常需要多轮预测与精炼，用更少的顺序轮次换取更多位置的并行处理。

第三：生成轮次少不等于推理成本低。

必须同时考虑每轮计算量、缓存复用、输出质量、吞吐与硬件效率。

第四：Mercury 类路线的价值在于探索不同的语言生成机制。

它不只是一个更快的模型名称，而是对逐 Token 生成范式的挑战。
