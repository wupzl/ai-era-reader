2026 年 10 月，上午 9:17。

林远坐在电脑前，正在调试一个复杂的 Java 项目。

屏幕上，PaymentService.java 抛出了一个令人头疼的异常。

他打开 AI 语音助手。

“帮我看看这个空指针异常，应该是第……”

话还没说完，AI 就回答：

好的，请把错误日志发给我。

林远皱了皱眉。

“我还没说完。”

AI 没有回应。

他继续说道：

“应该是第 137 行的 requestId 没有判空，但是……”

AI 又开始说话：

根据你的描述，可以增加空值校验……

“等等！你能不能先听我说完？”

AI 继续念着已经生成的答案。

林远忍无可忍，关闭了语音功能。

十分钟后，他找到架构师陈默。

“陈工，我们的语音 Agent 明明接入了最先进的大模型，为什么交流起来还像在使用十年前的语音客服？”

陈默没有回答。

他拿起手机，打开一个实时语音演示。

“林远，帮我分析一下……”

话说到一半，陈默突然停住。

AI 没有抢答。

两秒钟后，他继续：

“……这个支付系统的并发问题。”

AI 开始解释。

然而刚说了半句话，陈默突然插嘴：

“不对，我说的是重复回调，不是并发扣款。”

AI 立即停止原来的回答。

随后重新组织语言：

明白了，我们重点分析支付回调的幂等性问题。

林远睁大了眼睛。

“这不就是正常人类对话吗？”

陈默笑了。

“你终于发现问题了。”

过去的 AI 主要在学习如何回答问题。现在，我们开始让它学习如何参与交流。

第一幕：三个工厂组成的语音助手

陈默打开了林远编写的语音系统。

用户语音
   ↓
ASR：语音识别
   ↓
LLM：文本理解与生成
   ↓
TTS：语音合成
   ↓
AI 语音回答

“这套架构有问题吗？”陈默问。

林远回答：

“没有啊，业界用了很多年。”

“确实。它现在仍然很有价值。”

“但它有一个结构性特点。”

陈默在白板上画了三座工厂。

第一座工厂，把声音变成文字。

第二座工厂，把文字变成答案。

第三座工厂，把答案重新变成声音。

“每座工厂都很优秀，但它们之间需要交接。”

1. ASR：把声音变成文字

林远说：

“ASR 就是 Automatic Speech Recognition。”

“没错。”

陈默播放了一段录音。

我觉得这个 Redis 锁……嗯……可能不太对。

ASR 输出：

我觉得这个 Redis 锁可能不太对。

林远说：

“识别得挺准确。”

陈默问：

“可是中间的停顿、犹豫、语气呢？”

“丢了。”

“如果说话人是很不确定地提出猜测，和非常肯定地指出错误，这两种语气有没有区别？”

“有。”

“但是当下游 LLM 只能看到文字时，部分声学信息已经丢失了。”

陈默又播放两句话。

第一句：

你可真厉害。

第二句：

你可真厉害……

文字完全一样。

但第一句是真诚赞美。

第二句可能是讽刺。

“单纯的文本转写，不一定能保留这些信息。”

2. LLM：处理文本

ASR 完成后，文本被发送给语言模型。

{
  "role": "user",
  "content": "我觉得这个 Redis 锁可能不太对"
}

模型生成：

你可以检查锁的过期时间、释放方式以及是否存在误删其他请求锁的问题。

答案没有问题。

但 LLM 不知道用户是否还在说话。

也不知道用户刚才是在犹豫，还是已经说完。

因为在传统架构里，这些信息通常由其他组件负责处理。

3. TTS：把文字变回声音

最后，TTS 将回答合成为语音。

林远说：

“所以这套架构的主要问题，是信息在每个阶段之间不断转换。”

“对，但不能简单说转换就一定不好。”

陈默解释：

“模块化架构容易替换组件、检查转写结果、控制成本，也适合客服、会议转写和语音播报。”

“真正的问题是，当我们希望 AI 像人一样实时交流时，串行的处理流程会暴露局限。”

第二幕：延迟——一场由毫秒组成的战争

blog.toolzz.net

“你觉得语音助手为什么经常让人感觉反应迟钝？”陈默问。

林远回答：

“模型生成速度慢？”

“只是其中一个原因。”

陈默写下一条公式：

Tresponse=Tendpoint+TASR+TLLM+TTTS+Tnetwork T_{\text{response}} = T_{\text{endpoint}} + T_{\text{ASR}} + T_{\text{LLM}} + T_{\text{TTS}} + T_{\text{network}}

“这里是一个简化模型。实际流水线可以重叠执行，所以不一定完全相加。”

“我们做一个假设。”

阶段 假设耗时
等待判断用户说完 500 ms
ASR 完成当前转写 250 ms
LLM 生成首段回答 400 ms
TTS 生成首段声音 250 ms
网络及缓冲 100 ms
合计 1,500 ms

林远说：

“一秒半，好像也不是特别慢。”

陈默摇头。

“对一个网页问答来说，一秒半可能不错。”

“但面对面交流时，你说完一句话，对方每次都沉默一秒半，你会不会觉得奇怪？”

“会。”

“如果他还经常抢话、无法被打断呢？”

“那就更难受了。”

陈默说：

“实时语音交互优化的不只是模型推理速度。”

“它优化的是整个感知、决策和响应链路。”

1. 流水线并行

林远提出：

“我们能不能让 ASR 边听边转写，让 LLM 提前生成，让 TTS 边生成边播放？”

“当然可以。”

这叫流式流水线。

时间 →

用户语音：████████████████
ASR 转写：    ███████████████
LLM 生成：         ██████████████
TTS 合成：             █████████████
声音播放：                ███████████

“通过阶段重叠，可以显著减少等待。”

“但如果 ASR 的中间结果后来发生变化呢？”

林远回答：

“那 LLM 可能已经根据错误的转写开始回答了。”

“对。”

“所以实时系统需要在速度与稳定性之间权衡。”

第三幕：VAD——AI 怎样知道你说完了？

陈默突然停止讲解。

他看着林远。

三秒钟。

五秒钟。

林远终于忍不住问：

“陈工，你怎么不说了？”

陈默笑了。

“你刚才为什么没有立刻打断我？”

“因为我以为你在思考。”

“那你怎么判断我可能已经说完了？”

林远愣住。

“好像是根据停顿、语气和上下文。”

“这就是语音交互中的一个核心问题。”

什么时候应该开始回答？

1. VAD：Voice Activity Detection

VAD，即语音活动检测。

它的基本任务是判断当前音频片段中是否存在语音活动。

例如：

VAD 时间轴示意

示意音频能量变化。真实 VAD 不仅仅是音量阈值判断。

林远说：

“那只要连续静音 500 毫秒，就认为用户说完了？”

陈默问：

“假设用户说：”

这个问题我觉得……可能和事务隔离级别有关。

“中间停顿了一秒。”

“如果系统在停顿时开始回答，会怎么样？”

“它就抢话了。”

“没错。”

2. VAD 不等于轮次结束检测

陈默写下两个概念：

VAD：有没有人在说话。

Turn Detection：用户这一轮是否已经结束。

“这两件事情不是同一个问题。”

VAD 主要关注声音活动。

而轮次结束检测还可以结合：

  • 静音持续时间

  • 语音韵律

  • 语义是否完整

  • 说话人的停顿习惯

  • 当前对话状态

林远说：

“所以如果用户说‘我觉得这个方案……’，系统应该更倾向于等待。”

“对。”

“如果用户说‘这就是我的全部问题’，就可以更快地响应。”

“没错。”

但陈默又补充：

“语义判断也可能出错。真实系统通常需要组合多种信号，而不是完全依赖模型猜测。”

第四幕：从文字理解到原生音频模型

atse.in

当天晚上，陈默给林远展示了一条不同的技术路线。

它不再要求先把所有语音完整转成文字，再交给 LLM。

而是让模型直接处理音频表示。

林远问：

“声音不是连续信号吗？Transformer 怎么处理？”

陈默回答：

“和图像类似，首先需要把原始输入转换成模型可以处理的表示。”

1. 音频的数字化

人说话时，空气中的压力随时间变化。

麦克风将这种变化转换成电信号。

再经过采样和量化，得到数字音频。

例如：

原始声音
   ↓
采样波形
   ↓
音频特征 / 音频编码器
   ↓
模型内部表示

“传统 ASR 会把音频映射成文字。”

“而原生音频模型可以直接在音频表示上学习理解和生成。”

林远问：

“那它是不是完全不需要文字？”

“不一定。”

“不同系统可能采用音频编码器加语言模型、音频 Token、文本与音频联合建模等方式。”

“有些系统依然会利用文本监督和转写任务训练。”

“原生音频的重点不是彻底消灭文字，而是让模型能够直接利用音频信息，并可能直接生成语音。”

2. 音频 Token 是什么？

陈默举了一个例子。

普通语言模型处理：

["你好", "今天", "天气", "怎么样"]

音频生成模型可能处理一系列离散化的音频编码：

[a_102, a_087, a_231, a_054, ...]

“这些数字不是汉字。”

“它们代表某种学习到的音频表示。”

“通过音频解码器，可以把它们还原成声音。”

林远说：

“所以模型不一定需要先生成文字，再通过独立 TTS 转换？”

“对。有些架构可以直接预测音频表示，或者联合生成文本和音频。”

3. 原生音频模型的潜在优势

它可以更直接地利用：

  • 语调和情绪线索

  • 停顿与说话节奏

  • 说话人特征

  • 非语言声音

  • 音频与文本之间的对齐信息

但陈默提醒：

“原生音频不自动意味着更准确、更低延迟。”

“训练难度、数据质量、音频编码效率、流式解码方式和系统实现都很重要。”

第五幕：全双工——AI 终于学会边听边说

林远打开一段视频通话。

他问：

“传统语音助手和实时语音模型最大的体验差异是什么？”

陈默回答：

“一个重要差异是交互方式。”

1. 半双工式交互

在许多传统语音助手中，系统采用类似轮流发言的模式。

用户说话 → 用户停止 → AI 思考 → AI 回答 → 用户继续

当 AI 正在播放回答时，系统可能不接受新的用户语音，或者无法及时处理。

林远说：

“像对讲机。”

“对，虽然具体实现不一定严格是通信意义上的半双工。”

2. 全双工交互

全双工语音系统可以在播放 AI 声音的同时，继续接收和处理用户声音。

用户输入音频：████████      ███████████
AI 输出音频：       █████████████

“这意味着系统可以边说边听。”

陈默说。

“但这里有一个关键问题。”

“什么问题？”

“AI 播放的声音，也可能被麦克风重新采集。”

林远恍然大悟。

“它会听到自己的声音！”

“没错。”

这就是回声消除要解决的问题之一。

3. AEC：Acoustic Echo Cancellation

如果 AI 正在通过扬声器说：

你可以先检查 Redis 的过期时间……

麦克风可能同时采集到这段声音。

如果系统不加区分，就可能把自己的回答当成用户输入。

因此，实时语音系统通常需要考虑：

AEC：回声消除。

以及噪声抑制、自动增益控制等音频处理。

陈默说：

“真正的全双工不是简单地打开麦克风和扬声器。”

“而是让系统能够区分自己的声音、用户的声音和环境噪声。”

第六幕：打断机制——AI 为什么必须学会闭嘴？

larazon.es

某天，林远正在测试新的实时语音 Agent。

AI 开始解释：

Java 中的线程池主要由核心线程数、最大线程数、工作队列……

林远突然打断：

“不用讲基础概念，直接告诉我拒绝策略。”

AI 停顿了一瞬间。

随后回答：

明白。Java 线程池常见的拒绝策略包括 AbortPolicy、CallerRunsPolicy、DiscardPolicy 和 DiscardOldestPolicy。

林远笑了。

“这才对。”

陈默问：

“你觉得刚才系统内部发生了什么？”

“检测到用户开始说话，然后停止 TTS？”

“还不够。”

1. Barge-in：用户插话

Barge-in 指用户在系统回答过程中插话，系统能够及时响应。

完整处理通常包括：

  1. 检测新的用户语音。

  2. 判断是有效插话还是背景噪声。

  3. 停止或降低当前音频播放。

  4. 取消或暂停正在生成的回答。

  5. 更新对话状态。

  6. 根据新输入重新生成。

陈默说：

“这里最难的，不只是停止声音。”

“而是保持状态一致。”

2. 一个隐藏的状态问题

假设模型已经生成了下面这段回答：

Java 线程池有四种常见拒绝策略。第一种是 AbortPolicy，第二种是 CallerRunsPolicy，第三种是……

但用户只听到了：

Java 线程池有四种常见拒绝策略。

随后就打断了。

林远问：

“那对话历史里应该保存什么？”

陈默回答：

“这正是难点。”

“模型已经生成的内容，不等于用户实际听到的内容。”

如果系统把完整生成文本都当成已经说给用户听了，下一轮可能出现奇怪的情况。

例如，AI 说：

刚才提到的第三种策略……

但用户根本没有听到第三种策略。

所以系统需要区分：

  • 已生成内容

  • 已合成音频

  • 已发送音频

  • 估计已经播放的音频

  • 已确认的对话状态

林远说：

“原来打断机制还涉及音频播放进度和对话历史同步。”

“没错。”

“这已经是实时分布式状态管理问题了。”

第七幕：Interaction Models——不只是回答，而是参与

这些短反馈通常不是为了抢占话轮，而是表达正在倾听。

实时交互模型可以尝试学习类似行为。

但必须小心。

如果反馈太频繁，会显得烦人。

如果反馈太少，又会显得迟钝。

陈默补充：

“Interaction Models 不是单一、统一的模型架构名称。它更适合用来描述以实时互动行为为重点的一类研究方向。”

“实际系统可能使用独立的轮次预测模型，也可能把交互决策集成到多模态模型中。”

1. 视频为什么不能简单当成图片？

一张图片只有一个时间点。

而视频是一系列随时间变化的画面。

假设每秒 30 帧。

一分钟就有：

30×60=1800 30\times60=1800

帧。

如果把每一帧都完整送进视觉模型，计算和传输成本可能很高。

林远问：

“所以不能每帧都做完整视觉推理？”

“很多场景没必要。”

陈默解释：

“可以采用抽帧、事件触发、关键帧选择、视觉特征缓存等方法。”

2. 视频理解需要时间信息

陈默举了一个例子。

第三帧：

用户跳转到第 137 行

“如果模型只看到第三帧，它可能知道当前代码内容。”

“但如果理解了前面两帧，就更容易知道用户为什么跳转到这里。”

林远说：

“所以视频理解不仅要识别画面，还要理解画面之间的变化。”

“没错。”

实时多模态系统的核心挑战之一，是不同模态之间的时间同步。

第十幕：真正困难的是状态一致性

1. 推测执行与实际执行必须分离

陈默在白板上写下：

Predict ≠ Commit

“系统可以提前准备答案。”

“可以提前搜索文件。”

“可以提前计算可能的操作。”

“但涉及删除文件、修改数据库、发送消息、执行支付等有副作用的操作，必须等待足够明确的指令和权限判断。”

林远点头。

“所以实时 Agent 需要把操作分成只读和有副作用两类。”

“至少要有这样的区分。”

“而且还应该根据风险等级决定是否需要人工确认。”

2. 延迟与安全的矛盾

实时系统追求低延迟。

但安全系统需要确认。

两者天然存在张力。

陈默说：

“对于查询类操作，可以更积极地预取和推测。”

“对于高风险操作，宁愿慢一点，也不能把尚未说完的话当成最终授权。”

“这不是模型能力问题，而是系统设计原则。”

第六章：技术归档

Realtime Agent Runtime 交互与工具执行 权限、状态、一致性

本章最重要的五个结论

第一：传统 ASR → LLM → TTS 架构没有过时。

它仍然适合大量语音应用，但在低延迟、自然打断和音频信息保留方面可能受到结构限制。

第二：实时语音的关键不只是模型生成速度。

还包括 VAD、话轮检测、音频缓冲、回声消除、传输和取消机制。

第三：全双工不等于简单地同时打开麦克风和扬声器。

它需要系统能够持续感知、处理打断并维护一致的对话状态。

第四：实时多模态的难点是时间。

声音、画面、鼠标操作和工具结果必须正确对齐。

第五：实时 Agent 必须把推测与执行分开。

提前理解用户意图可以降低延迟，但不能把未确认的意图直接转换成高风险操作。
