kingservers.com

2026 年 12 月 7 日，凌晨 2:17。

天穹科技，人工智能平台研发中心。

距离下一代企业 AI 平台正式上线，已经过去了七个小时。

林远原本以为，今晚终于可以睡个好觉。

因为在上线之前，所有功能测试都已经通过。

RAG 知识问答准确率达到内部验收标准。

Coding Agent 可以自动修改代码、执行测试。

Agent OS 能够管理数千个任务。

模型网关支持多个模型供应商。

前端使用 Vue3，后端使用 Spring Boot 3。

PostgreSQL、Redis、RabbitMQ 全部正常运行。

甚至连 Kubernetes 集群都没有出现任何异常。

可就在此刻，监控室的警报突然响起。

PRODUCTION ALERT

HTTP Success Rate:       99.8%
Model API Success Rate:  99.6%
Database Status:         HEALTHY
Redis Status:            HEALTHY
RabbitMQ Status:         HEALTHY

User Satisfaction:       41.2%
Grounded Answer Rate:    63.7%
P95 Response Latency:    28.4s
Cost per Task:           +318%
Agent Task Success Rate: 52.1%

OVERALL PRODUCT STATUS: CRITICAL

林远盯着大屏幕，整个人都愣住了。

“这不可能。”

“接口成功率 99.8%。”

“数据库没有宕机。”

“模型 API 也没有报错。”

“为什么用户满意度只有 41%？”

陈默从身后走来。

他没有看服务器监控，而是打开了一条用户投诉。

我问的是公司最新的报销标准，AI 却引用了两年前已经废止的制度，而且说得非常肯定。

第二条：

我让 Coding Agent 修复一个空指针异常，它修改了 12 个文件，还把原本正常的接口改坏了。

第三条：

我只是问一个简单问题，为什么等了 30 秒？

第四条：

昨天这个功能还是好的，今天突然开始胡说八道。

林远喃喃道：

“可是系统明明没有故障……”

陈默拿起笔，在白板上写下一句话。

系统可用，不等于产品可靠。

随后又写下一句。

模型返回了答案，不等于用户的问题得到了解决。

“林远。”

“你已经学会了怎样构建 AI。”

“但你还没有学会怎样让 AI 在真实世界里长期可靠地运行。”

“今天，是你的最后一课。”

第一幕：Demo 为什么总是比生产环境聪明？

陈默没有立即修改系统。

他让林远打开上线前的演示录像。

视频里，一名员工问：

“公司的差旅报销标准是什么？”

AI 在两秒内回答：

“根据《差旅管理制度》，普通员工住宿标准为每晚 500 元。”

随后附上文档引用。

所有人鼓掌。

林远说：

“你看，Demo 完全正常。”

陈默问：

“演示时用了多少份文档？”

“20 份。”

“生产环境呢？”

“86 万份。”

“演示时有多少并发用户？”

“一个。”

“生产环境呢？”

“峰值几千个。”

“演示时文档会不断更新吗？”

“不会。”

“生产环境呢？”

“每天都有新文档上传。”

陈默点头。

“这就是问题。”

Demo 与生产环境的真正区别

维度 Demo 生产环境
数据规模 少量精选数据 海量、重复、过期、冲突数据
用户输入 设计好的问题 模糊、错误、恶意、超长输入
并发 单用户 大量用户同时访问
模型行为 少量成功案例 必须考虑概率性失败
系统依赖 相对稳定 网络、供应商、工具可能故障
成本 几次调用 数百万次调用
质量要求 能演示 可持续验证、回滚和改进

陈默说：

“传统软件的一个函数，在相同输入和环境下通常可以得到确定性结果。”

“但大模型应用还存在模型输出波动、知识来源变化和评测不完全覆盖的问题。”

“所以 AI 工程不能只关注程序有没有异常。”

“还必须关注结果有没有价值。”

林远问：

“那我们应该从哪里开始？”

陈默回答：

“先找到真正的故障。”

第二幕：Tracing——沿着一条错误答案追查整个系统

agentskill.asia

凌晨 2:39。

林远打开第一条投诉。

用户问题：

2026 年最新的差旅住宿标准是多少？

AI 回答：

普通员工每晚 500 元。

但真实的最新标准是 650 元。

林远第一反应：

“模型幻觉了。”

陈默反问：

“你怎么知道是模型的问题？”

“因为答案错了。”

“答案错了，不代表错误一定发生在生成阶段。”

“可能是检索错了。”

“可能是重排错了。”

“可能是文档版本错了。”

“也可能是 Prompt 没有正确约束模型。”

林远沉默了。

“那怎么查？”

“Tracing。”

1. 一次 AI 请求不是一次模型调用

陈默打开一条完整的 Trace。

Trace ID: 8f3c...

POST /api/chat
  │
  ├── Auth Check                  12ms
  ├── Query Rewrite              180ms
  ├── Embedding                   95ms
  ├── Vector Retrieval           130ms
  ├── Metadata Filtering          18ms
  ├── Reranking                  310ms
  ├── Context Assembly            24ms
  ├── LLM Generation            2840ms
  └── Response Validation         36ms

“Trace 是一次请求的完整执行链路。”

陈默解释。

“Span 则表示其中的某个操作。”

“每个 Span 可以记录开始时间、结束时间、状态、错误和必要的业务属性。”

2. 找到错误发生的位置

林远打开 Retrieval Span。

发现检索结果：

Top 1:
《差旅管理制度（2024）》
住宿标准：500 元
score: 0.92

Top 2:
《差旅管理制度（2026）》
住宿标准：650 元
score: 0.89

林远愣住。

“原来最新文档检索到了。”

“但旧文档排名更高。”

陈默问：

“那模型为什么选择旧文档？”

林远打开 Context Assembly。

发现系统只保留 Top 1。

最新文档被截断了。

“原来不是单纯的模型幻觉。”

“对。”

“这是检索排序、版本治理和上下文构造共同导致的错误。”

3. AI Observability 要监控什么？

传统监控通常关注：

CPU。

内存。

QPS。

错误率。

响应时间。

但 AI 系统还需要关注：

检索命中质量。

上下文 Token 数量。

模型版本。

Prompt 版本。

工具调用成功率。

Agent 步骤数。

生成答案的证据支持程度。

单任务成本。

用户反馈。

陈默说：

“Observability 的目的不是让仪表盘变得更漂亮。”

“而是当用户说 AI 错了时，你能知道它究竟错在哪里。”

第三幕：RAG——真正困难的不是向量检索，而是知识治理

林远重新检查 RAG 系统。

它使用：

PostgreSQL 17。

pgvector。

语义分块。

向量检索。

Metadata Rerank。

文档引用。

从技术结构上看，没有明显问题。

陈默问：

“你们怎样判断一份文档是否仍然有效？”

林远回答：

“我们有上传时间。”

“上传时间等于生效时间吗？”

“不一定。”

“那如果一份旧制度今天重新上传呢？”

林远沉默。

陈默继续问：

“如果两个部门发布了相互矛盾的制度呢？”

“如果某份文档只适用于成都分公司呢？”

“如果用户没有权限查看财务部门的内部文件呢？”

林远终于明白。

“RAG 不只是检索相似文本。”

“还需要管理知识的版本、权限、适用范围和有效性。”

1. RAG 的完整链路

用户问题

Query Understanding

意图识别 · 改写 · 权限上下文

Retrieval

关键词 / 向量召回 · Metadata Filter

Reranking & Context Assembly

重排 · 去重 · 版本选择 · Token 预算

LLM Generation

基于证据生成回答

Evidence Validation

引用检查 · 结果输出 · 反馈记录

2. 为什么要保留 Heading Path？

陈默打开一份文档。

《差旅管理制度》
  └── 第三章：费用标准
       └── 第二节：住宿费用
            └── 成都地区

“如果只截取正文：‘普通员工 650 元’，会丢失什么？”

林远回答：

“文档名称、章节路径和适用地区。”

“对。”

“所以分块时保留 Heading Path，不只是为了方便展示。”

“它还可以帮助模型理解文本的语义范围。”

例如：

{
  "documentId": "travel-policy-2026",
  "headingPath": [
    "第三章 费用标准",
    "第二节 住宿费用",
    "成都地区"
  ],
  "effectiveFrom": "2026-01-01",
  "status": "ACTIVE",
  "region": "CHENGDU"
}

3. Metadata Filter 与 Rerank 谁先执行？

林远问：

“是不是所有文档都先向量召回，然后再重排？”

陈默摇头。

“不是。”

“权限、租户和明确的业务适用范围，应该尽可能在检索阶段就作为硬约束。”

“不能先检索出无权访问的内容，再寄希望于模型不要泄露。”

例如：

SELECT id, content, embedding <=> :queryVector AS distance
FROM document_chunk
WHERE tenant_id = :tenantId
  AND status = 'ACTIVE'
  AND region IN ('GLOBAL', :region)
ORDER BY embedding <=> :queryVector
LIMIT 20;

陈默提醒：

“这只是示例。”

“生产环境还要正确处理文档级 ACL、用户权限、索引和查询性能。”

“向量相似度解决的是相关性，不是授权问题。”

4. RAG 的三个不同质量指标

林远原本只统计最终回答正确率。

陈默要求拆分：

Retrieval Recall@K： 应该找到的相关证据，是否出现在前 K 个检索结果中？

Context Relevance： 放进 Prompt 的上下文是否真正有用？

Answer Faithfulness： 答案中的事实主张是否得到提供证据的支持？

“这些指标不能互相替代。”

陈默说。

“如果 Recall 很低，应该优先优化检索。”

“如果 Recall 很高但答案仍然编造事实，应该检查上下文构造、生成和验证。”

第四幕：Agent——执行成功，不等于任务成功

windowsforum.com

凌晨 3:21。

林远开始调查 Coding Agent 的投诉。

用户要求：

修复订单查询接口的空指针异常，不要修改公开 API。

Agent 最终输出：

已完成修复。

但实际上：

它修改了 12 个文件。

删除了一段异常处理逻辑。

还更改了公开方法签名。

林远愤怒地说：

“它明明违反了用户要求，为什么状态还是 COMPLETED？”

陈默问：

“你们怎样判断任务完成？”

“模型返回了 final answer。”

陈默摇头。

“这是把模型声明当成了事实。”

1. Agent Completion 与 Task Success

一个 Agent 可能：

成功调用工具。

成功修改文件。

成功输出总结。

但仍然没有完成用户目标。

因此，至少需要区分：

Execution Completed
≠
Task Successfully Solved

2. 验证层

陈默设计了多层验证。

第一层：工具执行是否成功。

第二层：代码是否能编译。

第三层：相关测试是否通过。

第四层：是否违反用户约束。

第五层：是否引入回归。

第六层：是否需要人工审批。

“并不是所有任务都能完全自动验证。”

陈默说。

“但能够验证的部分，应该尽量交给确定性的工具。”

3. 为什么 Agent 需要预算？

林远问：

“如果测试失败，让 Agent 一直重试直到成功，不就行了吗？”

陈默回答：

“如果它陷入错误方向呢？”

“如果它每次修改都破坏更多文件呢？”

“如果模型调用成本不断增长呢？”

“所以需要执行预算。”

例如：

maxSteps = 60
maxToolCalls = 100
maxDuration = 15 minutes
maxModelCost = $2.00

“这些数字只是示例，实际预算应按任务类型制定。”

“Agent 需要知道什么时候继续，什么时候停止，什么时候升级给人工。”

第五幕：评测体系——如果没有考试，你怎么知道 AI 进步了？

林远终于意识到：

他们上线前的测试集只有 50 个问题。

而生产环境每天有数十万次请求。

“陈工，我们需要更大的评测集。”

1. Cost per Successful Task

假设：

模型 A 每次任务成本 0.1 美元。

成功率 50%。

模型 B 每次任务成本 0.15 美元。

成功率 90%。

如果每次尝试独立、成功率稳定且允许重复尝试，那么期望成功成本近似为：

[ C_{\text{success}}=\frac{C_{\text{attempt}}}{P_{\text{success}}} ]

模型 A：

[ 0.1/0.5=0.20 ]

模型 B：

[ 0.15/0.9\approx0.167 ]

“模型 B 单次更贵，但在这个简化假设下，成功任务的期望成本更低。”

陈默说。

“实际系统还要考虑失败重试是否独立、任务不可重复的副作用以及人工处理成本。”

对长工具输出进行压缩。

缓存可复用结果。

避免重复 Embedding。

限制上下文长度。

为租户设置预算。

第十幕：延迟优化——为什么 P95 比平均值更重要？

5 次非常慢。

平均值可能仍然不算太差。

P95 表示大约 95% 的观测请求延迟不超过该值。

[ T_{\text{total}}= T_{\text{queue}}+ T_{\text{retrieval}}+ T_{\text{rerank}}+ T_{\text{prefill}}+ T_{\text{decode}}+ T_{\text{other}} ]

“这是简化的串行路径。”

“如果存在并行调用，总延迟需要按照实际依赖关系计算，不能简单把所有阶段相加。”

TTFT：Time to First Token。

用户等待第一个 Token 的时间。

Total Latency：

整个请求完成的时间。

“流式输出对交互体验很重要。”

“但如果首 Token 之前的检索和排队已经耗时 15 秒，SSE 也救不了。”

1. 四种常见缓存

Embedding Cache。

相同文本、相同 Embedding 模型版本可以复用向量结果。

Retrieval Cache。

Prompt Cache。

某些推理服务可以复用公共 Prompt 前缀的计算结果，具体取决于模型和服务实现。

Response Cache。

缓存最终回答，适合相对稳定、低风险且上下文一致的任务。

“因为生产工程从来不是一次性完成的。”

“它是一个持续监控、评估、修复和改进的过程。”

林远看着屏幕上不断流动的请求。

突然想起第一章。

那时候，他只想让模型做出正确判断。

第二章，他研究不同的生成方式。

第三章，他让 Agent 能够持续工作。

第四章，他让 Agent 拥有记忆。

第五章，他让多个模型协作。

第六章，他让 AI 听见和看见世界。

第七章，他让 AI 理解三维空间与动作。

第八章，他把模型放进端侧设备。

第九章，他为 Coding Agent 建立 Harness。

第十章，他设计了 Agent OS。

第十一章，他理解了不同模型架构的取舍。

而现在——

他终于明白，真正困难的并不是让 AI 在一次演示中表现得聪明。

而是让 AI 在数百万次真实请求中，仍然尽可能可靠地帮助用户完成任务。

第十二章：技术归档

领域 核心问题 典型工程手段
RAG 如何获得可靠知识 分块、混合检索、重排、版本与权限治理
Agent 如何可靠执行任务 状态机、预算、工具验证、沙箱
Model Gateway 如何管理多模型 路由、限流、熔断、回退
Evaluation 如何衡量质量 Golden Dataset、回归评测、人工校准
Observability 如何定位问题 Metrics、Logs、Tracing
Versioning 如何复现行为 Prompt、Model、知识库版本
A/B Testing 如何比较方案 随机分流、主要指标、护栏指标
灰度发布 如何降低上线风险 分阶段放量、监控、回滚
Cost Control 如何控制成本 模型路由、缓存、Token 预算
Latency Optimization 如何提升响应体验 TTFT、并行化、SSE、缓存
幻觉治理 如何降低无依据回答 证据约束、引用验证、拒答
Security 如何控制风险 ACL、最小权限、Prompt Injection 防护
Data Flywheel 如何持续改进 反馈、失败分类、评测、迭代

本章最重要的五个结论

第一：AI 系统的成功率，不等于 HTTP 请求成功率。

真正重要的是用户目标是否完成。

第二：RAG 的难点不只是向量检索。

知识版本、权限、有效期、冲突和引用验证，都是生产级 RAG 的关键问题。

第三：Agent 的最终回答不能直接作为任务完成证明。

必须尽可能通过测试、工具结果和业务约束进行验证。

第四：AI 平台必须把 Prompt、模型、知识库和工具都视为可版本化依赖。

否则线上问题难以复现，系统行为也难以追踪。

第五：真正的 AI 工程是一套持续改进体系。

评测、观测、灰度、成本、安全和数据闭环，决定了 AI 产品能否长期可靠运行。

天穹科技顶楼。
