2026 年 10 月，凌晨 3:17。

实验室的灯还亮着。

林远站在一台人形机器人面前，神情紧张。

“向前走三步，然后拿起桌上的红色杯子。”

机器人抬起头。

摄像头开始采集画面。

数据通过网络发送到云端。

三秒后，机器人终于做出了反应。

但就在机械臂伸向杯子的瞬间——

屏幕右上角的网络图标变成了红色。

Connection lost.

Cloud inference unavailable.

Robot task suspended.

机械臂停在了半空。

林远愣住了。

“不是吧？只是断了个网，机器人就不会动了？”

陈默从实验室另一端走了过来。

“你的机器人，究竟有没有自己的大脑？”

“当然有，它接入了一个很强的多模态模型。”

“模型在哪里？”

“云端 GPU 集群。”

“所以它的大脑在几千公里之外。”

林远沉默了。

陈默拿起一块巴掌大小的开发板。

“如果我告诉你，我们可以把一个数十亿参数的模型放进这块设备里呢？”

林远皱起眉头。

“不可能吧？大模型不是需要几十 GB，甚至几百 GB 显存吗？”

陈默笑了。

“那是因为你还把模型的参数数量、参数精度、运行内存和计算能力混为一谈。”

他在白板上写下：

模型大，不代表每个参数都必须用 32 位存储。

“今天，我们要把一座庞大的 AI 数据中心，缩小到一块芯片上。”

第一幕：云端帝国的四道枷锁

陈默没有立即介绍量化。

他先问林远：

“为什么我们一定要研究端侧模型？”

林远回答：

“因为断网之后，云端模型用不了。”

“这是第一条。还有呢？”

第一条枷锁：网络延迟

云端推理的响应时间可以简化为：

Tcloud=Tupload+Tqueue+Tinference+Tdownload T_{\text{cloud}} = T_{\text{upload}}+ T_{\text{queue}}+ T_{\text{inference}}+ T_{\text{download}}

陈默解释：

“模型计算再快，也无法完全消除网络传输时间。”

“尤其是实时机器人、智能眼镜和语音助手。”

“如果每次决策都要跨网络请求云端，交互可能变得迟钝。”

林远问：

“所以本地模型一定更快？”

“不一定。”

“如果端侧芯片太弱，本地推理可能比云端更慢。”

“真正需要比较的是端到端延迟，而不是只看网络耗时。”

第二条枷锁：推理成本

陈默打开一份假设账单。

一家 AI 公司每天处理一百万次请求。

每次请求都调用昂贵的旗舰模型。

“如果其中 80% 只是简单分类、摘要和意图识别呢？”

林远回答：

“那我们在浪费大量计算资源。”

“对。”

“云端每次请求都可能消耗 GPU 时间、显存带宽、网络和调度资源。”

“而端侧模型可以利用用户已有设备的算力，减少部分云端推理负担。”

但陈默补充：

“端侧计算并不是没有成本。它会消耗电池、内存、芯片资源，还需要承担模型分发与更新成本。”

第三条枷锁：数据隐私

林远提出：

“如果用户使用 AI 分析私人文档，把内容发送到云端，就涉及数据传输和服务端处理。”

“没错。”

“而在本地完成推理，可以减少敏感数据离开设备的机会。”

“不过本地推理不等于绝对安全。设备被入侵、日志泄露、模型缓存和遥测配置，都可能造成风险。”

第四条枷锁：离线可用性

陈默拿起机器人控制器。

“如果机器人在地下矿井呢？”

“如果手机处于飞行模式呢？”

“如果工业设备与外网物理隔离呢？”

林远终于明白。

“有些场景不是云端不够好，而是根本不能依赖云端。”

陈默点头。

“所以端侧 AI 的意义，不只是便宜。”

“更是让智能真正进入设备本身。”

第二幕：七十亿参数，到底占多少内存？

udacity.com

“我们从最基础的问题开始。”

陈默在白板上写下：

7B Parameters

“假设一个模型有 70 亿个参数。”

“每个参数需要占多少空间？”

林远回答：

“看使用什么数据类型。”

“很好。”

1. FP32：每个参数 4 字节

FP32 是 32 位浮点数。

一个参数占：

32 bits=4 bytes 32\text{ bits}=4\text{ bytes}

70 亿个参数：

7×109×4=28×109 bytes 7\times10^9\times4=28\times10^9\text{ bytes}

也就是约 28 GB（十进制），约 26.1 GiB。

“光是模型权重，就要这么多空间。”

陈默说。

“注意，这还没有计算 KV Cache、运行时缓冲区和其他开销。”

2. FP16：每个参数 2 字节

FP16 是 16 位浮点数。

同样的模型：

7×109×2=14 GB 7\times10^9\times2=14\text{ GB}

林远眼睛一亮。

“内存直接减半。”

“对。”

“但 FP16 并不总能完整保留 FP32 的数值行为，尤其涉及动态范围和数值稳定性时。”

“此外，还有 BF16 等常见格式。它同样占 16 位，但指数范围与 FP16 不同。”

3. INT8：每个参数 1 字节

如果把权重量化为 8 位整数：

7×109×1=7 GB 7\times10^9\times1=7\text{ GB}

“从 28 GB 变成 7 GB。”

林远说。

“这已经是原来的四分之一。”

4. INT4：每个参数 4 位

如果进一步压缩到 4 位：

7×109×48=3.5 GB 7\times10^9\times\frac{4}{8}=3.5\text{ GB}

林远猛地站起来。

“等等！”

“一个 70 亿参数的模型，理论上只需要 3.5 GB 就能存下权重？”

“对，这是理想的纯权重计算。”

“实际模型文件还需要量化尺度、零点、元数据，以及可能保留高精度的部分张量。”

“运行时也需要额外内存。”

量化前后的权重体积

70 亿参数模型 · 理论权重占用

采用十进制 GB；不含量化元数据、KV Cache 和运行时开销。

陈默看着林远。

“现在你知道，为什么一个原本需要高显存设备的模型，有机会运行在手机或普通电脑上了吗？”

林远点头。

“因为我们可以减少每个参数的存储位数。”

“没错。”

“但新的问题来了。”

“原本用 16 位表示的数，压缩到 4 位，精度不会损失吗？”

第三幕：量化——让数字学会舍弃不重要的细节

陈默拿起一张纸。

上面写着一组参数：

0.127
0.259
-0.843
1.532
-0.076

“假设这些是神经网络权重。”

“如果用 FP16 或 FP32，可以表示大量不同的数值。”

“但如果只有 4 位呢？”

林远回答：

“4 位只能表示 16 种不同的编码。”

“对。”

“我们需要把原来的连续或高精度数值，映射到有限的离散等级。”

1. 量化的基本公式

对于一种常见的仿射量化方式：

q=clip⁡(round⁡(xs)+z,qmin⁡,qmax⁡) q=\operatorname{clip}\left( \operatorname{round}\left(\frac{x}{s}\right)+z, q_{\min},q_{\max} \right)

其中：

  • xx：原始浮点值

  • ss：量化尺度（Scale）

  • zz：零点（Zero Point）

  • qq：量化后的整数值

反量化近似恢复：

x^=s(q−z) \hat x=s(q-z)

陈默解释：

“你可以把量化理解成把连续刻度变成有限档位。”

“原来一个数字可以精细到很多小数位。”

“现在只能落在有限的刻度上。”

“这就产生了量化误差。”

2. 量化误差为什么不一定毁掉模型？

林远问：

“神经网络有几十亿参数，每个参数都有误差，岂不是会严重影响结果？”

陈默回答：

“这是量化技术的核心难点。”

“但模型中不同权重、不同层、不同通道对精度的敏感程度并不一样。”

“有些数值误差对最终输出影响较小。”

“有些关键层或异常值则非常敏感。”

“所以量化不是简单地把所有参数粗暴截断。”

实际工程可能采用：

  • Per-tensor 或 Per-channel 量化

  • 分组量化（Group-wise）

  • 权重与激活值分别量化

  • 对敏感层保留更高精度

  • 使用校准数据降低误差

陈默说：

“核心思想是尽可能把有限的精度预算分配到重要位置。”

3. PTQ 与 QAT

林远问：

“是不是必须重新训练模型？”

“不一定。”

PTQ：Post-Training Quantization，训练后量化。

先训练出模型，再对权重进行量化，必要时使用校准数据。

QAT：Quantization-Aware Training，量化感知训练。

在训练或微调过程中模拟量化带来的数值影响，让模型适应低精度表示。

“PTQ 部署方便，成本相对低。”

“QAT 可能获得更好的精度表现，但需要额外训练。”

“具体选择要看模型结构、目标硬件和精度要求。”

第四幕：量化不等于一定加速

ey.com

林远把模型从 FP16 量化到了 INT4。

模型文件缩小了很多。

但实际测试结果却让他震惊。

“陈工，为什么模型变小了，推理速度反而没快多少？”

陈默反问：

“你认为模型推理速度由什么决定？”

“计算量？”

“还有呢？”

“内存读取速度？”

“很好。”

1. 计算瓶颈与带宽瓶颈

模型推理可能受到两类主要资源限制。

一种是计算能力。

例如矩阵乘法需要大量运算。

另一种是内存带宽。

尤其在某些小批量、自回归解码场景中，每生成一个 Token，都需要访问大量模型权重。

陈默写下一个近似关系：

Tweight-read≈权重读取字节数有效内存带宽 T_{\text{weight-read}}\approx \frac{\text{权重读取字节数}}{\text{有效内存带宽}}

“假设模型权重有 14 GB。”

“有效带宽是 140 GB/s。”

“那么理想情况下，仅仅读取一遍权重就需要大约 0.1 秒。”

“当然，这只是非常粗略的下界估算，不代表真实推理耗时。”

林远说：

“如果 INT4 把权重缩小到 3.5 GB，那么理论读取时间就能降低。”

“对。”

“但前提是硬件和推理内核能高效处理这种量化格式。”

2. 为什么 INT4 有时不快？

因为实际运行可能需要：

读取 INT4 权重。

解包。

反量化或使用专门的低精度计算内核。

执行矩阵运算。

如果硬件不支持高效 INT4 运算，解包和转换可能带来额外开销。

此外，长上下文、大批量推理时，瓶颈也可能转移到注意力计算、KV Cache 或其他部分。

陈默总结：

模型文件更小，不代表推理必然更快。

“真正的性能优化，需要结合硬件、算子实现和具体工作负载。”

第五幕：蒸馏——让小学生向教授学习

meta-intelligence.tech

几天后。

林远发现一个问题。

“量化只是改变参数精度。”

“但一个 70B 模型，即使量化到 INT4，也还有约 35 GB 的理论权重。”

“手机还是很难运行。”

陈默点头。

“所以我们需要第二条路线。”

“不是让同一个模型存得更小。”

“而是训练一个真正参数更少的模型。”

他写下：

Knowledge Distillation，知识蒸馏。

1. Teacher 与 Student

假设我们有两个模型。

Teacher：70B 大模型。

Student：3B 小模型。

大模型已经具备很强的推理和任务处理能力。

现在，我们希望小模型学习它的部分行为。

Teacher Model · 大模型

生成软标签、答案、轨迹或其他训练信号

Distillation Dataset / Loss

Student Model · 小模型

学习目标任务上的行为

林远说：

“这是不是相当于让大模型给小模型出题，并告诉它答案？”

“这是其中一种做法。”

“但蒸馏还可以利用概率分布、隐藏表示或其他训练信号。”

2. 软标签为什么有价值？

陈默举了一个分类例子。

假设任务是判断一句话的情绪。

传统硬标签：

积极：1
消极：0
中性：0

而教师模型可能给出：

积极：0.70
消极：0.10
中性：0.20

“这些概率包含了类别之间的相对关系。”

“Student 不只是学习哪个类别正确，还可以学习教师对其他类别的判断。”

经典知识蒸馏可以使用类似目标：

L=αLhard+(1−α)T2DKL(pT∥pS) \mathcal L = \alpha\mathcal L_{\text{hard}} + (1-\alpha)T^2 D_{\mathrm{KL}}(p_T\Vert p_S)

其中 TT 是蒸馏温度，pT,pSp_T,p_S 分别表示教师与学生经过温度调整后的概率分布。

“对于生成式语言模型，也可以使用教师生成的数据进行监督微调。”

陈默说。

“但学习教师生成的答案，不等于完全复制教师的内部能力。”

3. 小模型为什么能接近大模型？

林远问出了最关键的问题。

“一个 3B 模型，参数只有 70B 的一小部分。”

“为什么有时还能接近它的效果？”

陈默回答：

“因为你要区分通用能力与特定任务能力。”

“70B 模型可能掌握非常广泛的知识和能力。”

“但你的任务可能只需要其中一小部分。”

例如，一个企业内部模型只负责：

识别工单类别。

抽取合同字段。

生成固定格式 SQL。

判断代码是否符合某种规范。

第七幕：KV Cache——模型为什么越聊越吃内存？

zoer.ai

某天晚上。

林远终于在一台内存有限的设备上运行起了量化模型。

刚开始，一切正常。

“记得。”

“那你应该知道，模型生成下一个 Token 时，需要利用之前 Token 的信息。”

1. 自回归生成

传统自回归语言模型通常逐 Token 生成。

例如：

输入：Java 的 HashMap 是

生成 1：一种
生成 2：基于
生成 3：哈希表
生成 4：实现
……

每生成一个新 Token，都需要处理它与历史上下文的关系。

“如果每次都从头重新计算全部历史 Token 的 Key 和 Value，会产生大量重复计算。”

陈默说。

“因此，推理系统通常会缓存历史 Token 的 Key 和 Value。”

这就是：

KV Cache。

2. KV Cache 保存什么？

在 Transformer Attention 中：

Q=XWQ,K=XWK,V=XWV Q=XW_Q,\quad K=XW_K,\quad V=XW_V

模型可以缓存历史 Token 对应的 K、V 表示。

当新 Token 到来时，只需要计算新 Token 的相关表示，并与历史缓存进行注意力计算。

林远说：

“所以 KV Cache 是用内存换计算。”

“对。”

“它能避免大量重复投影计算，但缓存本身会随着上下文长度增加。”

3. KV Cache 占用计算

对于常见的缓存布局，可以近似估算：

MKV=2×L×Hkv×D×S×B M_{\text{KV}}= 2\times L\times H_{\text{kv}}\times D\times S\times B

其中：

  • LL：Transformer 层数

  • HkvH_{\text{kv}}：每层 KV Head 数量

  • DD：每个 Head 的维度

  • SS：上下文 Token 数

  • BB：每个缓存元素的字节数

最前面的 2，代表 Key 和 Value。

假设一个示例模型：

层数 L = 32
KV Heads = 8
Head Dimension = 128
Context Length = 32768
KV Precision = FP16（2 字节）

那么：

MKV=2×32×8×128×32768×2 M_{\text{KV}} =2\times32\times8\times128\times32768\times2

约为 4 GiB。

林远倒吸一口凉气。

“也就是说，模型权重可能只有 3.5 GB，但 KV Cache 就可能额外占 4 GiB？”

“在这组假设参数下，是的。”

“而且实际运行还有其他缓冲区和内存开销。”

4. MHA、MQA 和 GQA

陈默继续解释。

“为什么刚才只用了 8 个 KV Heads？”

“因为不是所有模型都采用传统多头注意力的相同 KV 结构。”

在经典 Multi-Head Attention（MHA）中，通常每个 Query Head 对应自己的 Key 和 Value Head。

MQA（Multi-Query Attention）让多个 Query Head 共享一组 Key/Value Head。

GQA（Grouped-Query Attention）则让一组 Query Heads 共享 Key/Value Heads。

“这样可以显著减少 KV Cache 体积。”

“这也是端侧推理与高并发服务中非常重要的模型架构优化。”

FP16 / BF16 16 位浮点表示 降低权重存储与带宽需求

本章最重要的五个结论

第一：模型参数数量不等于运行内存。

实际部署需要考虑权重精度、KV Cache、激活和运行时开销。

第二：量化主要解决表示与存储问题，不保证一定加速。

真实速度取决于硬件、算子、带宽和推理场景。

第三：蒸馏与量化不是一回事。

量化压缩参数表示，蒸馏让小模型学习大模型的部分能力。

第四：KV Cache 是长上下文推理的重要内存来源。

上下文越长，缓存通常越大。GQA、MQA、缓存量化等技术可以缓解这一问题。

第五：端侧 AI 的真正目标不是取代所有云端模型。

而是在延迟、成本、隐私、离线能力与模型质量之间建立合理的系统架构。
