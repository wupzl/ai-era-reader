## 第一幕：一万个数字员工，为什么会让公司瘫痪？

林远不理解。

“陈工，我们的每个 Agent 单独运行都没有问题。”

“为什么放在一起就出问题了？”

陈默反问：

“假设一台计算机只有一个程序。”

“它还需要复杂的进程调度吗？”

“不太需要。”

“如果同时运行一万个程序呢？”

“就需要操作系统管理 CPU、内存、文件和进程。”

陈默点头。

“Agent 系统正在遇到类似的问题。”

### 1. 从单 Agent 到多 Agent

最初的 Agent 架构很简单。

```
用户
 ↓
Agent Runtime
 ↓
LLM + Tools + Memory
 ↓
任务结果
```

林远说：

“这就是我们第三章实现的持久化 Agent。”

“对。”

“但当系统拥有几千个 Agent 时，会出现新的问题。”

谁先运行？

谁可以使用 GPU？

谁可以调用昂贵的模型？

谁可以访问生产数据库？

一个 Agent 崩溃后，任务由谁接管？

多个 Agent 同时修改同一份记忆，谁说了算？

任务执行到一半，服务器宕机怎么办？

“这些问题不属于某个 Agent 的局部推理。”

陈默说。

“它们属于整个系统的资源管理与协调问题。”

### 2. Agent OS 是什么？

陈默在白板上写下：

> Agent OS：一种以 Agent 为主要执行实体，统一管理任务、状态、资源、权限、工具和协作关系的系统架构。

他特别补充：

“Agent OS 目前并不是一个拥有统一标准定义的操作系统类别。”

“不同项目可能把 Agent 框架、运行时平台或多智能体编排系统称为 Agent OS。”

“我们这里讨论的是一种工程架构思想，不是说它一定要取代 Linux 或 Windows。”

林远问：

“所以它更像运行在传统操作系统之上的 Agent 管理层？”

“在我们要设计的系统里，是这样。”

## 第二幕：Agent Runtime 与 Agent OS，到底差在哪里？

陈默画出两座建筑。

左边是一间办公室。

右边是一座城市。

“Agent Runtime 像单个员工的工作环境。”

“Agent OS 则像管理整座城市的基础设施。”

### 1. Runtime 负责单个 Agent

一个 Agent Runtime 通常管理：

模型调用。

工具执行。

上下文。

局部状态。

执行循环。

Checkpoint。

权限检查。

林远点头。

“这部分我们已经实现过。”

### 2. Agent OS 负责整个 Agent 群体

Agent OS 需要进一步管理：

跨 Agent 的任务调度。

资源分配。

全局权限策略。

共享工具注册。

事件路由。

持久化任务队列。

分布式 Worker。

故障恢复。

监控与审计。

Agent Runtime 与 Agent OS 的层次关系

Agent OS

全局调度 · 资源治理 · 权限 · 状态协调

Coding Runtime

Research Runtime

Data Runtime

基础设施

数据库 · 消息队列 · 模型服务 · 沙箱 · 操作系统

陈默说：

“这里有一个非常重要的区别。”

“Runtime 解决的是 Agent 如何执行。”

“OS 解决的是大量 Agent 如何被组织、约束和协调。”

## 第三幕：Agent 调度——谁有资格先获得算力？

![KI-Scheduler übernehmen die operative Steuerung von Unternehmen](https://images.openai.com/static-rsc-4/76UNW1H_7EPwtmgKZIDvwRY3snTxsePMGX3bsUdjGQzUDQ5JsfFNg810-Dhkbjj3UEwwdFgu3XgLGFtHrNG_FdPbaPp9TPctMMmNgoiZYsjaYjZtTch3t_oFzOi3ZD3UH0lhsz6cEYnZvDpC1tbIh3bJXBcFsSdcuLEWAVGDU78?purpose=inline)

[ad-hoc-news.de](https://www.ad-hoc-news.de/boerse/news/ueberblick/ki-scheduler-uebernehmen-die-operative-steuerung-von-unternehmen/68661632)

监控室里。

一万个 Agent 正在争夺有限资源。

林远提出：

“那我们是不是可以直接用线程池？”

陈默反问：

“线程池能解决什么？”

“限制并发线程数，复用线程。”

“那它知道哪个 Agent 更重要吗？”

“不知道。”

“知道一个 Agent 的 Token 预算吗？”

“不知道。”

“知道哪个任务正在等待用户确认吗？”

“也不知道。”

### 1. 线程池不是 Agent 调度器

陈默解释：

“线程池是执行资源管理工具。”

“但 Agent 调度需要处理业务优先级、任务状态、资源需求和外部依赖。”

例如：

一个普通 Research Agent 可以晚几分钟执行。

但一个正在处理生产故障的 Agent，可能需要更高优先级。

“所以调度器要理解任务，而不只是理解线程。”

### 2. 任务优先级

陈默设计了三类任务。

```
P0：紧急生产故障
P1：用户交互任务
P2：后台批处理任务
```

但他立刻补充：

“不能永远只执行 P0。”

“否则低优先级任务可能一直得不到资源。”

“这叫饥饿。”

林远说：

“可以使用 Aging，让等待时间越长的任务逐渐提高有效优先级。”

“对。”

“也可以采用加权公平调度、配额或分租户队列。”

### 3. Agent 调度需要考虑哪些资源？

传统 CPU 调度主要关注 CPU 时间等资源。

而 Agent 调度还需要考虑：

模型调用并发。

Token 消耗。

GPU 推理容量。

工具调用速率。

沙箱容器数量。

数据库连接。

网络请求配额。

林远突然说：

“所以 Agent 调度本质上是一个多资源调度问题。”

陈默点头。

“而且很多资源并不在本机。”

“模型可能由远端 API 提供。”

“工具可能是第三方服务。”

“因此 Agent OS 还需要处理分布式限流和外部服务故障。”

## 第四幕：生命周期——Agent 不是只有运行和结束

林远打开数据库。

发现任务状态只有两个。

```
RUNNING
COMPLETED
```

陈默看了一眼。

“这就是你们故障恢复困难的原因之一。”

“为什么？”

“因为现实中的 Agent 不只有运行和完成。”

### 1. Agent 生命周期状态机

陈默重新设计了状态。

CREATED

任务已创建

QUEUED

等待调度

RUNNING

正在执行

WAITING

等待工具或用户

SUSPENDED

主动挂起

RETRYING

准备重试

COMPLETED

FAILED

CANCELLED

示意状态集合，实际状态转移需要由明确规则约束，并非所有状态都能直接互相转换。

### 2. 为什么需要 WAITING？

陈默举例：

Agent 准备执行生产数据库迁移。

权限系统要求用户确认。

此时 Agent 不应该持续占用执行线程。

它应该：

保存当前状态。

释放计算资源。

进入 WAITING。

等用户批准后恢复执行。

林远说：

“这和操作系统中的阻塞状态有点像。”

“对。”

“但 Agent 的等待可能持续几分钟、几小时，甚至几天。”

“所以不能简单地用一个阻塞线程一直等待。”

## 第五幕：持久化状态——服务器死了，Agent 不能跟着失忆

![The Agentic SRE: Why Autonomous Stacks Will Break Your Cloud (And How To Fix It) | by Damian Figiel | Mar, 2026 | Medium](https://images.openai.com/static-rsc-4/tOmohgVSYaaft_0Ir0JKWT6yEMpNGBPAA2KIQffEnv5t7DeuDPQ2PpiJHk-seAoy7SheXZR0u65a-4RiU1DrBlb8YAd7B-0JmZ9v_khrN0Rqe_GU_pFeyaE5xqToo7JO4DiWt0PXWrmcFTxi2cHU1Mg5rjE_ZqL6Fc-QIV1gfaA?purpose=inline)

[figiel.medium.com](https://figiel.medium.com/the-agentic-sre-why-autonomous-stacks-will-break-your-cloud-and-how-to-fix-it-594e62887506)

凌晨四点。

一台 Worker 服务器突然宕机。

上面正在运行 200 个 Agent。

林远急忙查看数据库。

“完了，这些任务的内存状态全没了。”

陈默问：

“你们没有持久化执行状态吗？”

“有聊天记录。”

“聊天记录等于执行状态吗？”

林远沉默。

### 1. Conversation 不等于 Execution State

聊天记录可能保存：

用户说了什么。

模型回答了什么。

工具返回了什么。

但恢复任务还需要知道：

当前执行到哪一步。

哪些工具已经执行。

哪些结果已经提交。

哪些操作仍在等待确认。

当前任务由哪个 Worker 持有。

重试次数是多少。

“所以 Agent OS 需要持久化状态机，而不仅是消息历史。”

### 2. Checkpoint

陈默设计了一份任务状态。

```
{
  "taskId": "task-1024",
  "agentId": "coding-agent-7",
  "status": "RUNNING",
  "step": 18,
  "checkpointVersion": 6,
  "lastCompletedAction": "run_tests",
  "nextAction": "inspect_failures",
  "retryCount": 1
}
```

“Checkpoint 是某个时刻的可恢复状态快照。”

陈默说。

“它可以包含上下文引用、工作目录、任务计划、工具执行记录和其他必要信息。”

“但不能把它理解成整个进程内存的完整镜像。”

### 3. 为什么 PostgreSQL 比单纯 Redis 更适合做持久化真相源？

林远问：

“我们已经有 Redis，为什么还要 PostgreSQL？”

陈默回答：

“Redis 很适合缓存、限流、短期租约和快速状态查询。”

“但对于需要事务约束、长期保存和复杂审计的任务状态，关系数据库通常更方便。”

“当然，Redis 也具备持久化机制，不能简单说 Redis 一定会丢数据。”

“关键在于你选择什么作为系统的权威状态源。”

在他们的设计里：

PostgreSQL 保存权威任务状态。

Redis 保存可重建的缓存、限流计数和短期协调信息。

## 第六幕：事件总线——Agent 为什么不能互相直接调用？

林远继续排查故障。

发现大量 Agent 之间使用同步 HTTP 调用。

```
Agent A → Agent B → Agent C → Agent D
```

只要 Agent D 响应慢，前面的任务就全部等待。

陈默问：

“如果 Agent B 崩溃呢？”

“Agent A 就会失败。”

“如果 Agent C 需要十分钟才能完成呢？”

“整个调用链都可能超时。”

陈默点头。

“所以我们需要把长任务协作从同步调用中解耦。”

### 1. Event Bus

事件总线允许系统通过事件传递状态变化。

例如：

```
TaskCreated
TaskAssigned
AgentStarted
ToolExecuted
AgentSuspended
AgentCompleted
AgentFailed
```

Agent 不必始终同步等待其他 Agent。

它可以发布事件。

由其他组件异步处理。

### 2. RabbitMQ 在 Agent OS 中的作用

陈默打开 RabbitMQ 管理界面。

“你之前在高并发履约系统中使用过消息队列。”

“还记得为什么使用吗？”

林远回答：

“削峰、异步解耦、失败重试。”

“对。”

“这些思想在 Agent OS 中仍然成立。”

但陈默强调：

“消息队列不是自动保证业务只执行一次的魔法。”

“消费者可能收到重复消息。”

“也可能在执行成功后、确认消息前宕机。”

“所以工具执行仍然需要幂等设计。”

## 第七幕：共享记忆——一万个 Agent 能否拥有共同的大脑？

![Grid Memory — Shared Memory for AI Agent Teams](https://images.openai.com/static-rsc-4/hRqMuY6tN97FWnHs3fz7wJxkOcfNveaLSvvVHmxjkZ-P5-wLSKnmOdWrrfYDy79sxc7905XDHkL8Dj7D_eWqhOwMkniYKU14xL9P9Wl9uV82rV9_Sgmi-7LQ8odGxy1awZXaT9cN-joM9lJPvYox50GvoNN6V3deJgFf0njTQ-o?purpose=inline)

[gridmemory.io](https://gridmemory.io/)

系统恢复后，新的问题出现了。

两个 Research Agent 同时更新同一份项目知识。

Agent A 写入：

```
项目当前使用 PostgreSQL 17。
```

Agent B 根据过期文档写入：

```
项目当前使用 PostgreSQL 15。
```

结果共享记忆出现冲突。

林远问：

“是不是直接让所有 Agent 共享同一个向量数据库就行？”

陈默摇头。

“向量数据库解决的是相似性检索，不自动解决事实一致性。”

### 1. 三种记忆层次

陈默设计：

私有记忆。

只属于某个 Agent 或任务。

例如当前代码修改计划。

共享工作记忆。

多个 Agent 在同一任务中共享。

例如任务状态、接口约定和执行结果。

长期知识记忆。

跨任务保存的知识。

例如项目规范、架构文档和历史经验。

### 2. 为什么共享记忆需要版本控制？

陈默问：

“如果两个 Agent 同时修改同一个事实，应该怎么办？”

林远回答：

“可以用乐观锁。”

“对。”

例如：

```
UPDATE shared_memory
SET content = :newContent,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
```

如果更新行数为零，说明版本发生变化。

Agent 需要重新读取并决定如何处理冲突。

“这和数据库并发控制的思想完全一致。”

陈默说。

“因为共享记忆本质上也是共享状态。”

### 3. 记忆污染

林远又想到一个问题。

“如果某个 Agent 从恶意网页中提取了一条错误信息，并写入共享记忆呢？”

陈默点头。

“这就是记忆污染风险。”

“因此长期记忆最好保留来源、时间、可信度和访问权限等元数据。”

“不能让任意 Agent 把未经验证的内容直接写成全局事实。”

## 第八幕：权限隔离——Agent 之间也需要边界

林远查看权限配置。

发现所有 Agent 使用同一个数据库账号。

陈默看了一眼。

“这太危险了。”

“为什么？”

“因为一个 Research Agent 根本不需要拥有生产数据库的写入权限。”

### 1. 最小权限原则

不同 Agent 应该拥有不同的权限范围。

Coding Agent：

允许访问指定代码仓库。

Testing Agent：

允许运行测试，但不一定允许修改生产配置。

Research Agent：

允许访问授权的网页和文档。

Deployment Agent：

可能需要部署权限，但必须受到严格控制。

“Agent OS 应该统一管理这些权限。”

陈默说。

“而不是把所有凭证直接交给模型。”

### 2. 能力令牌

陈默提出一种思路。

当 Agent 需要执行某个操作时，系统签发具有明确范围和有效期的能力令牌。

例如：

```
{
  "agentId": "coding-agent-7",
  "resource": "repo:payment-service",
  "actions": ["read", "write"],
  "expiresAt": "2026-11-15T10:00:00Z"
}
```

“这只是概念示例。”

“实际系统还需要签名验证、撤销机制和安全存储。”

“关键是 Agent 不应该因为拥有一个工具，就自动拥有该工具背后的全部权限。”

## 第九幕：工具注册中心——谁来管理整个 Agent 世界的工具？

![AWS Bedrock AgentCore Registry: First Impressions from the Preview](https://images.openai.com/static-rsc-4/4lvQAHwSrVk1hQpSPbwe6n5eRrN7tL_yFD9VA0mqzCXWaxlmSVDeKKyeyPTDevEjh3kisDoDDub8cdoaUjJTZKDvkDaU9e-IAGEa8ogVN5A9WggRnJUKjIcERfRVDUjnmAE-TvU54z0ZEtTT7sTbr9cKlqu_9Ax2o9rc03FkCGA?purpose=inline)

[my2cents.ai](https://www.my2cents.ai/deep-dive/aws-agentcore-registry/)

林远发现，每个 Agent 都维护着自己的工具列表。

Coding Agent 有一份。

Research Agent 有一份。

Data Agent 又有一份。

工具版本彼此不一致。

陈默问：

“如果数据库工具升级了，谁来通知所有 Agent？”

林远回答：

“现在只能逐个修改配置。”

“所以需要统一工具注册中心。”

### 1. Tool Registry

工具注册中心可以保存：

工具名称。

能力描述。

输入输出 Schema。

版本。

服务地址。

权限要求。

健康状态。

调用限制。

### 2. MCP 的位置

林远问：

“那 MCP 是不是 Agent OS？”

陈默摇头。

“MCP 主要提供模型应用与外部工具、资源等能力之间的标准化连接方式。”

“它本身不等于完整的 Agent 调度、状态持久化或资源治理系统。”

“Agent OS 可以使用 MCP 作为工具接入层。”

林远终于开始设计分布式执行架构。

他问：

“如果一个 Agent 任务被分配给 Worker A。”

“Worker A 突然宕机。”

“Worker B 怎么接管？”

陈默回答：

“需要任务所有权和故障检测机制。”

### 1. Lease：租约

调度器把任务分配给 Worker A。

同时记录租约。

```
Task: task-1024
Owner: worker-A
Lease Expire: 10:00:30
```

Worker A 需要定期续租。

如果租约过期，系统可以认为该 Worker 可能已经失去任务执行能力。

随后尝试重新分配任务。

### 2. 为什么仅有 Lease 还不够？

林远问：

“租约过期后直接让 Worker B 执行，不就行了？”

陈默摇头。

“假设 Worker A 只是网络短暂中断。”

“它没有真正停止执行。”

“此时 Worker B 也开始执行。”

“就可能出现两个 Worker 同时处理同一个任务。”

林远脸色一变。

“脑裂。”

“对。”

### 3. Fencing Token

陈默提出：

“我们可以为每次任务所有权变更分配递增的 Epoch。”

例如：

```
Worker A: epoch = 7
Worker B: epoch = 8
```

任务状态更新时，需要校验 Epoch。

旧 Worker 即使恢复，也不能覆盖新 Worker 的状态。

“但要注意，Fencing Token 只有在相关存储或资源侧实际校验时才有效。”

“对于无法识别 Epoch 的外部工具，还需要幂等键、操作日志或其他保护措施。”

## 第十一幕：故障恢复——为什么 Exactly Once 这么难？

凌晨五点。

林远终于重启了系统。

但很快收到一条告警。

```
Duplicate payment issued.
```

他震惊了。

“我们明明使用了 RabbitMQ！”

“为什么还会重复执行？”

陈默问：

“你们什么时候 ACK 消息？”

“工具执行成功之后。”

“那如果工具已经执行成功，但 ACK 之前 Worker 宕机呢？”

林远沉默。

“消息会重新投递。”

“然后工具可能再次执行。”

### 1. At-Least-Once 与幂等

陈默解释：

“很多消息队列消费方案采用至少一次交付语义。”

“这意味着消息可能重复。”

“所以业务必须考虑幂等。”

例如发券任务：

```
INSERT INTO coupon_issue_record
    (request_id, user_id, status)
VALUES
    (:requestId, :userId, 'PENDING')
ON CONFLICT (request_id) DO NOTHING;
```

“这可以利用唯一约束避免重复创建同一请求记录。”

“但完整履约还需要状态机、事务边界、重试和外部发券接口的幂等支持。”

### 2. Transactional Outbox

林远问：

“如果数据库状态更新成功，但 RabbitMQ 消息发送失败呢？”

陈默回答：

“可以使用 Transactional Outbox。”

在同一个数据库事务中：

更新任务状态。

写入待发送事件。

提交事务。

随后由独立发布器把事件发送到 RabbitMQ。

“这样可以避免数据库事务提交成功、但事件完全没有持久化记录的问题。”

“但消息仍然可能重复发布，因此消费者依然需要幂等。”

### 5. Spring Boot 调度服务

```
@Service
public class AgentSchedulerService {

    private final AgentTaskRepository repository;
    private final AgentEventPublisher publisher;

    public AgentSchedulerService(
            AgentTaskRepository repository,
            AgentEventPublisher publisher) {
        this.repository = repository;
        this.publisher = publisher;
    }

    @Transactional
    public void dispatchNext(String workerId) {
        AgentTask task = repository.claimNext(workerId);

        if (task == null) {
            return;
        }

        // 在同一数据库事务中写入 Outbox 事件
        publisher.appendOutbox(
            task.id(),
            task.epoch(),
            "AGENT_TASK_ASSIGNED"
        );
    }
}
```

陈默提醒：

“这里的 `appendOutbox` 必须真正写入同一个事务所管理的数据库。”

“不能在事务中直接发送 RabbitMQ，然后假装数据库和消息队列具有原子事务。”

### 6. Worker 执行循环

```
public void executeTask(AgentTask task) {

    AgentCheckpoint checkpoint =
        checkpointRepository.load(task.id());

    while (!checkpoint.isFinished()) {

        verifyLease(task.id(), task.epoch());

        AgentAction action =
            agentRuntime.nextAction(checkpoint);

        ToolResult result =
            toolExecutor.execute(action);

            checkpoint.apply(result);

        checkpointRepository.save(
            task.id(),
            task.epoch(),
            checkpoint

    }
}
```

## 第十四幕：Agent OS 与工作流平台，到底有什么区别？

林远突然提出：

“陈工，这套系统看起来很像 Temporal、Airflow 或其他工作流平台。”

“那 Agent OS 是不是换了个名字？”

陈默笑了。

“这是一个非常好的问题。”

### 1. 工作流平台

传统工作流系统通常擅长：

明确的任务依赖。

重试。

调度。

状态持久化。

定时执行。

分布式任务协调。

例如：

```
上传文档
   ↓
解析文档
   ↓
生成 Embedding
   ↓
写入向量数据库
```

这类流程相对确定。

### 2. Agent OS 的特殊需求

Agent 任务可能是动态的。

模型在执行过程中决定下一步。

工具调用路径可能不断变化。

任务可能产生新的子任务。

模型可能请求用户确认。

上下文可能需要压缩和恢复。

多个 Agent 可能协作、争论和重新规划。

陈默说：

“但这些能力并不意味着传统工作流平台完全做不到。”

“实际上，Agent OS 可以建立在成熟的工作流引擎之上。”

“区别更多在于它是否针对 Agent 的动态推理、上下文、工具和权限提供专门抽象。”

### 3. 两者对比

|维度|传统工作流平台|Agent OS 架构|
|---|---|---|
|核心执行单元|任务、Activity、Job|Agent、任务、工具动作|
|执行路径|通常更明确|可能由模型动态决定|
|状态管理|工作流状态|工作流状态 + Agent 上下文|
|调度|任务与资源调度|任务、模型预算与工具资源调度|
|权限|服务与任务权限|Agent 身份、工具与资源权限|
|恢复|任务重试与恢复|任务恢复 + 推理上下文恢复|
|关系|可作为基础设施|可基于工作流平台实现|

林远终于明白。

“所以 Agent OS 不是必须从零重新造一个调度器。”

“没错。”

“工程上最重要的不是名字。”

“而是你是否真正解决了 Agent 的执行与治理问题。”

## 第十章：技术归档

|技术|核心问题|典型实现|
|---|---|---|
|Agent Runtime|单个 Agent 如何执行|Agent Loop、工具、上下文|
|Agent OS|大量 Agent 如何协调|调度、状态、权限、资源治理|
|Task Scheduler|谁先执行|优先级、配额、公平调度|
|Lifecycle|Agent 处于什么状态|状态机|
|Checkpoint|宕机后如何恢复|PostgreSQL、对象存储|
|Event Bus|Agent 如何异步协作|RabbitMQ|
|Shared Memory|多 Agent 如何共享知识|PostgreSQL、pgvector|
|Permission System|谁能访问什么|RBAC、能力令牌、策略引擎|
|Tool Registry|如何管理工具|MCP、Schema Registry|
|Distributed Execution|如何跨机器执行|Worker、Lease、Epoch|
|Failure Recovery|如何避免重复副作用|幂等、Outbox、重试|
|Workflow Engine|如何编排任务|DAG、状态机、持久化工作流|

### 本章最重要的五个结论

第一：Agent Runtime 与 Agent OS 的关注范围不同。

Runtime 关注单个 Agent 的执行，Agent OS 关注大量 Agent 的全局协调和治理。

第二：Agent OS 的核心不只是模型调用。

调度、权限、状态、故障恢复和资源管理，都是系统可靠运行的必要部分。

第三：共享记忆也是共享状态。

它需要版本控制、权限隔离、来源追踪和一致性策略。

第四：分布式 Agent 必须接受重复执行的现实。

Lease、Fencing Token、幂等、Outbox 和状态机共同降低故障风险，不能只依赖消息队列。

第五：Agent OS 不一定需要从零构建。

成熟的工作流引擎、数据库、消息队列和容器平台，可以成为它的重要基础设施。
